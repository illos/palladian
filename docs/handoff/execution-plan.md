# Palladian implementation and review plan

Read [the specification](../specs/palladian-platform-v1.md) first. This plan makes its requirements executable in bounded increments. No phases have been implemented or accepted.

## Working agreement

- Implement one assigned phase at a time. Do not start downstream phases to make an incomplete core phase appear useful.
- Routine UI and internal implementation decisions belong to the implementer. Changes to the protected contracts require a written proposal and reviewer decision.
- Protected contracts: auth/session lifecycle, identity and data isolation, collaborative persistence, agent scopes, file authorization/lifecycle, domain trust, and destructive data operations.
- A review checkpoint is requested by the owner’s chosen implement-then-review workflow. It is not permission to deploy or to modify the old application.
- Where possible make one coherent commit per phase or bounded subphase. Record the base and head commit IDs. Do not stage unrelated changes. If the workspace has no Git repository, initialize one before implementation, with a suitable ignore file and no secrets.
- Inspect local instructions and applicable skills. Use current official documentation and installed package types. Do not type a guessed library API and hide failures with `any`, `@ts-ignore`, fake generated files, or disabled tests.
- If a phase is too large, split it into named subphases before coding. Complete and review the risky subphase first. Do not treat an entire platform as a one-shot task.
- Fixture data and test-only identities stay in isolated environments. A test auth bypass must never be deployable in production.
- Do not deploy production, alter DNS, migrate real data, rotate existing secrets, or modify `/srv/presidium/projects/deltos/code` under this handoff. Prepare reproducible artifacts and runbooks; request specific authorization only when an actual external action is ready.

## Suggested repository layout

This is an implementation default. Preserve clear ownership if a tool requires different layout.

```text
apps/web/                     Vite app, routes, shell, lazy app registry, PWA assets
apps/web/src/apps/notes/       Notes UI
apps/web/src/apps/recipes/     Recipes UI
packages/contracts/           pure types, validation schemas, resource/operation contracts
packages/ui/                  theme tokens and shared UI primitives
packages/app-sdk/             typed host context and optional tool adapters
convex/                       all deployed backend source
convex/platform/              authorization, instances, files, search, schedules, grants
convex/apps/notes/             Notes server functions and schema fragments
convex/apps/recipes/           Recipes server functions and schema fragments
infra/cloudflare/             static hosting config and necessary edge handlers
tests/                        cross-cutting integration and browser tests
docs/decisions/               short decisions with evidence
docs/reviews/                 phase reports and independent review results
```

Generated Convex types must be generated by the actual toolchain. Root `convex/schema.ts` composes app schema fragments. Client-safe contracts cannot import server secrets or server runtime modules. Enforce import boundaries with tooling, not comments alone.

## P0 — Establish the build and resolve compatibility

**Deliver:** workspace, minimal themed shell, CI/build scripts, typed definition/instance/resource interfaces, two empty lazy app entries, and `docs/decisions/0001-runtime-and-auth.md`.

The decision records pinned versions of React/Vite/Convex/Better Auth/integration/MCP candidates, package compatibility evidence, browser support, auth transport options, and proposed session policy. Include a dependency diagram showing browser, Cloudflare, Convex, and auth request origins. Identify provider-specific versus platform user IDs.

The MCP target is official TypeScript SDK v2 with protocol `2026-07-28` only. Record how older-protocol handling will be explicitly disabled, including SDK defaults. No speculative legacy implementation belongs in P0. Client-specific protocol evidence and any justified compatibility exception belong to P5.

Produce an auth compatibility spike in an isolated development environment if available. A complete P0 report must state which behaviors were exercised, not merely that packages installed. Never fabricate successful deployment or browser testing if credentials/tools are unavailable.

**Tests/evidence:** strict typecheck, production build, lazy-chunk graph, version/peer-dependency report, source import boundaries. No fake data implementation disguised as a backend.

**Checkpoint:** independent review of architecture and compatibility before P1. Unresolved library compatibility does not authorize changing the chosen stack.

## P1 — Prove identity, sessions, and startup

**Deliver:** private owner provisioning, real sign-in/out, stable platform identity mapping, session list/revoke, auth readiness states, redacted diagnostics, initial shell independent of network auth. Design recovery/TOTP now and implement before real-data adoption; make any pilot-only recovery limitation prominent.

Use the supported Better Auth lifecycle. Record exact session expiry/sliding settings and credential persistence. Resolve whether a supported cross-domain adapter or reviewed first-party route is used. Do not carry the old 3-second abort, account-wide reuse response, or hard logout on 5xx.

**Tests/evidence:** A01–A07 and U01 below, plus the reviewed design for A08. Implemented recovery/TOTP may satisfy A08 now; otherwise carry it explicitly to P9 and keep the pilot on development data. Use real auth integration for refresh and persisted-session tests; unit mocks alone cannot prove this phase. Test server-side revocation with an unexpired access JWT.

**Checkpoint:** protected-core review. Downstream phases must not begin on top of failing refresh/revocation behavior. Real iPhone verification may remain clearly pending in a development pilot but blocks v1 acceptance.

## P2 — App instances, authorization, and platform APIs

**Deliver:** create/list/rename/archive instances, workspace ownership, typed server registration, consistent errors, pagination, revisions/idempotency, shared routing/resource resolver, and scoped preferences.

Use two test users, at least two workspaces, and two instances of the same app definition. Public endpoint authorization must derive identity and verify parent relationships. Scope helper imports are mandatory for app functions; direct database access remains server-only.

**Tests/evidence:** D01–D06 for the entities implemented in this phase. Carry file-byte lifecycle portions of D02/D06 to P3 and actual app-form coverage to P4. Enumerate all public functions and their authorization checks. Demonstrate stale structured edits returning a conflict without discarding local form contents.

**Checkpoint:** protected-core review before adding private content or file bytes.

## P3 — Files and cross-app search

**Deliver:** R2 adapter, upload/finalize/download lifecycle, reference tracking, safe deletion/reconciliation, reusable uploader, search projection registry, scoped search UI, export skeleton.

Implement using small fixture files and text records before wiring editors. File and search functions must use the same resource authorization helpers as app operations.

**Tests/evidence:** F01–F06 and S01–S04 using scoped fixture resources/projection builders; rerun actual Notes/Recipes navigation and projection freshness in P4. At least one real R2 integration test proves upload, server verification, download, failed finalization, and deletion against a test bucket. Fault-inject external failures; do not require a live outage to prove retry behavior.

**Checkpoint:** protected-core review, especially private-file URL issuance, orphan cleanup, and search leakage.

## P4 — Notes and Recipes vertical slices

Split into P4a collaborative Notes and P4b Recipes if needed. Review P4a persistence before broadening its UI.

**Deliver Notes:** required editor features, attachment integration, current-document export, trash/restore, revision/recovery view, correct acknowledgement-based save status, and shared protocol for future agent changes.

**Deliver Recipes:** create/edit/list/search, ordered ingredients and steps, servings, optional photo, scoped settings, export, and trash/restore. Use typed app data and semantic mutations. A recipe is not serialized into a note body.

**Tests/evidence:** E01–E07 plus V01–V03, and app-integrated D/S checks carried from P2/P3. For E06 call the actual server operation with a test agent principal; exercise its MCP transport again in P5. Real two-client convergence test uses independent browser contexts and an actual Convex development deployment. Assert final document content on server and both clients. Include specific preserved edits, not just equal hashes of possibly empty documents.

**Checkpoint:** protected-core editing review and owner-facing UI review. P0–P4 accepted constitutes the foundation pilot only.

## P5 — Agent API and MCP

Split P5a scoped tool server/manual token and P5b OAuth connector flow. P5b has its own compatibility checkpoint before implementation.

**Deliver:** operation discovery, list/search/fetch/invoke, typed validation, scoped write grants, audit metadata, manual token management, OAuth discovery/consent/PKCE/refresh/disconnect using compatible maintained libraries, and canonical resource URLs.

Use the exact same domain functions as UI. Agent note edits must participate in collaboration. Define bounded tool results and input limits. Fetch/search are read-only; write operations cannot be disguised as fetch.

**Tests/evidence:** M01–M10. Exercise a real MCP client with manual token. Separately test ChatGPT, Codex, and Claude Code, with actual surface/version, supported opt-ins, observed protocol revision, and connection/reconnection evidence. A local simulated client does not prove compatibility with any of those products. Start with new-protocol-only serving. Add the smallest legacy adapter only after a required client's lack of support is confirmed under the specification's evidence policy; unavailable access or missing docs is pending evidence, not a reason to add fallback code.

**Checkpoint:** protected-core review of credential handling and authorization. If OAuth libraries are incompatible, document a concrete reviewed alternative; leave P5b incomplete until resolved.

## P6 — Scheduler and notification inbox

**Deliver:** registered one-shot/daily operations, occurrence idempotency, edit/cancel, status/retries, timezone policy, durable scoped notification inbox. Demonstrate a recipe reminder delivered once to the shared inbox and linked to the correct recipe.

**Tests/evidence:** J01–J05. Use controllable clocks for recurrence tests and an actual scheduled development execution for integration. Include stale queued job after cancellation and transient external failure.

**Checkpoint:** focused review of job authorization, cancellation, and duplicate effects. OS push/email remain excluded rather than silently stubbed.

## P7 — Voice and Deck adapters

**Deliver:** lazy voice capture/transcription/preview/insertion, provider abstraction, cleanup/cancel/error behavior; opt-in custom Deck, native fallback, editor adapter, shared command pipeline. Record source provenance for reused Deltos code.

**Tests/evidence:** I01–I05. Verify actual iOS keyboard/viewport behavior, microphone denial, recording cancellation, switching target while transcription is pending, and preservation of ordinary typing/undo. Desktop emulation does not satisfy iOS evidence.

**Checkpoint:** input regression review before declaring the optional tools ready for other apps.

## P8 — Standalone apps, PWA installs, and custom-host binding

**Deliver:** integrated/direct routes, per-instance manifests/icons, minimal standalone chrome, safe service-worker lifecycle, verified operator-managed custom-host bindings and documented setup/removal. No self-service domain dashboard required.

**Tests/evidence:** R01–R07. Install Palladian, Notes, and Recipes on a real iPhone. Verify distinct launches and persistent independent sessions; edit the same resource from two entry points. Use a real authorized test domain for custom-host evidence. Unknown/removed hosts must not resolve as another app.

**Checkpoint:** domain/auth/PWA review. If no domain or phone access is available, provide the prepared test procedure and mark those tests pending; do not claim v1 complete.

## P9 — Release readiness and developer handoff

**Deliver:** minimal runnable new-app template, app-authoring guide, complete requirements/evidence map, measured performance report, export/restore drill, recovery/TOTP completion, dev/staging/prod runbook, release/rollback plan, redacted diagnostics, operator session/grant management.

The app-authoring guide must let an agent build another small typed app through registration and app-owned code without changing auth, storage internals, global search implementation, or shell routing logic. Schema composition and registry entries are expected edits; scattered core patches are a failure.

**Tests/evidence:** O01–O05 and implemented A08; close every carried acceptance item, rerun affected critical suites and the final end-to-end flow. Run `install --frozen-lockfile`, typecheck, lint, tests, production build, and actual backend validation against the selected development deployment. Use project scripts with documented names.

**Checkpoint:** independent release review. Present deployment/import as a separate concrete decision. No production deployment is authorized by passing tests alone.

## Phase report template

Create `docs/reviews/Px-implementation.md` with:

```text
Phase and base/head commits:
Outcome and user-visible behavior:
Changed files and why:
Protected contracts touched:
Pinned dependencies changed and evidence:
Acceptance IDs -> test paths/commands/results:
Real integration/device checks performed:
Mocks used and what they do NOT prove:
Performance measurements if relevant:
Known failures, pending evidence, and limitations:
Spec deviations requiring review:
How to reproduce and revert this phase:
Next permitted phase after acceptance:
```

Reviewer creates a separate `Px-review.md`: accepted / changes required / blocked by missing evidence, with severity-ranked findings tied to file/line and requirement ID. “Tests passed” alone is not acceptance of a broken architectural contract. A pending device test must remain visible through all subsequent reports.

## Independent reviewer checklist

1. Compare actual code to this spec, not just the implementer's report. Inspect the full relevant diff and callers.
2. Trace public function authorization and negative cases from credentials to records, files, search and jobs.
3. Examine real auth integration: credentials, renewal, retry, revocation, multiple tabs, cold start, and session persistence. Look for reintroduced Deltos failure paths.
4. Confirm one authoritative note representation and one write protocol shared by humans and agents.
5. Check external side-effect retry semantics, R2 cleanup races, and signed-URL leakage.
6. Check that app definitions are trusted code and no false sandbox claims or generic privileged escape endpoints exist.
7. Reproduce critical tests; inspect assertions so equal empty results or all-denied endpoints cannot pass as success.
8. Verify imported code provenance, bundle boundaries, library support and meaningful test coverage.
9. Separate code correctness from unperformed integration/iOS/domain checks. Neither substitute for the other.
10. Require fixes with a regression test for substantive failures, then review the revised diff. Do not expand scope opportunistically.
