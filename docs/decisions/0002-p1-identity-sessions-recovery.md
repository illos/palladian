# ADR 0002 — P1 browser lifecycle and recovery design

Status: implemented for local development, **awaiting independent protected-core review**. Date: 2026-09-09. This does not approve hosted auth, production or personal-data adoption. Read ADR 0001 and the complete P0 correction review alongside this decision.

## Identity and private provisioning

Only the operator-invoked internal `provision:owner` action enables the library's signup API in its private instance, with automatic sign-in disabled. The public auth factory always disables signup. No bootstrap secret or privileged browser endpoint exists. Better Auth performs email validation, password hashing and credential account creation. Password length is 16–128 characters; account names are 1–100 characters. Repeating provisioning cannot overwrite an existing password (Better Auth's generic duplicate response deliberately does not disclose whether an account exists). This is provisioning, not recovery.

`platform/identity:ensure` derives the provider subject from a verified **live** session and transactionally creates/reads the unique `(better-auth, subject)` mapping. Concurrent first logins yield the same platform ID. `current` returns only that platform ID or null for an invalid session. Email is never an ID. P2 will use these generated platform IDs for workspace ownership; P1 does not create workspaces or instances. Provider account deletion/recreation and provider migration must preserve or explicitly relink platform identity through a separately reviewed operation; email matching cannot relink accounts.

Session listing checks the live auth user, scopes by that subject and paginates 25 records. Only session IDs, creation/expiry timestamps and the current-session flag leave the application API. Revoke resolves the target server-side, checks same-user ownership, then invokes the supported Better Auth revoke API with server-only credentials. This preserves the library's sensitive-action freshness policy. Public calls cannot pass an owner ID or session token to the platform API. No user agent, IP, credential or profile appears in diagnostic export.

## Lifecycle and origin arrangement

Adopt the official `crossDomainClient`, `convexClient` and `ConvexBetterAuthProvider` for the **local-development proof**. Browser frontend is exactly `http://localhost:5173`, auth HTTP is `http://127.0.0.1:3215`, and Convex data is `http://127.0.0.1:3214`. There is no proxy. Hosted adoption remains blocked pending the actual Cloudflare/Convex HTTPS arrangement and independent review.

The official cross-domain adapter persists its credential in JavaScript-readable localStorage (`palladian_cookie`), sends `Better-Auth-Cookie` with `credentials: omit`, and consumes `Set-Better-Auth-Cookie`. This is not HttpOnly storage. Both server cookie cache and client session-data cache are disabled. Temporary access JWTs are cached in the official provider's memory **and** the adapter also sets its 900-second `better-auth.convex_jwt` cookie at sign-in/token issuance; cross-domain transport persists that cookie in the same JavaScript-readable jar as `better-auth.session_token`. This is not memory-only JWT storage. P1 does not manually rehydrate that JWT cookie into the provider. Application modules never acquire tokens or receive credentials. Every installation/origin may have an independent long session.

Exact policy: session `expiresIn=31_536_000` seconds, `updateAge=86_400`, `freshAge=86_400`, sliding enabled, access JWT `expirationSeconds=900`. Daily activity extends expiration by a full year. Freshness is a separate library check on sensitive account operations, not an idle cutoff on navigation or data access. There is no absolute annual logout or extra idle timer. Convex custom-JWT validation has a five-second clock-skew allowance ([verifier source](https://github.com/get-convex/convex-backend/blob/main/crates/authentication/src/lib.rs)); the preliminary probe checked at encoded expiry +2 seconds and did not throw (it did not distinguish a null denial from an authorized result), so the final rejection/resume test waits beyond +5 seconds and recognizes the query's explicit null-denial contract. This verifier tolerance is distinct from the configured 900-second JWT lifetime. Every protected operation checks the live session, so server revocation takes effect before JWT expiry. P5 agent grants have separate records/lifetimes; P1 contains no grants to test.

Only an exact configured frontend origin is trusted; configuration rejects wildcard/non-origin values and requires HTTPS except localhost development. Social sign-in and cross-domain one-time-token verification paths are disabled for P1. No social provider or OAuth-provider package is installed. P0's custom-header Node-origin observation remains relevant; browser CORS is not a substitute for hosted CSRF/callback testing.

The shell renders independently of an asynchronously loaded auth region. Account/sign-in UI is separately lazy. A startup session check distinguishes an authoritative null session from transport errors before mounting the provider. Errors keep credentials and offer retry. Retry replaces the Convex client/provider and their cached account state, while the supported client retains the device credential. The supported provider remains the only production token-acquisition owner. There are no per-app refresh timers, custom rotations, three-second aborts or account-wide reuse responses.

Explicit logout unmounts private state before network completion. The official cross-domain client deletes local credentials as it starts signout; therefore a failed signout cannot claim server revocation succeeded. The UI reports unconfirmed revocation and directs the owner to revoke from another session. Storage events reset the private region only when the session credential changes, not when its sliding expiry metadata changes. No private application data or drafts exist yet; P2/P4 must extend this boundary to actual caches and recoverable drafts.

## Declaration compatibility discovered in P1

The auth runtime versions are unchanged: Better Auth 1.6.30, adapter 0.12.5, Convex 1.45.0. Browser imports expose defects absent from the P0 server-only spike. Three patched packages change **declarations only**, never runtime JavaScript:

- Adapter `AuthClient` previously used an open union including an arbitrary plugin, causing inferred session data to become `never`. The patch instantiates the actual supported convex/cross-domain plugin tuple. It does not assert/cast our client into a false type.
- Better Auth's organization `getActiveMemberRole` declaration indexed a generic intersection that TypeScript 7 cannot prove has `role`; conditional role inference preserves the return relationship without ignoring the error. No organization feature is enabled.
- The adapter's component schema declaration is regenerated from its unchanged packaged `src/component/schema.ts` with the pinned TypeScript compiler, strict mode and exact-optional checking. The published expanded declaration included explicit undefined on optional stored fields and violated Convex's document constraint. This is actual declaration generation, not a fabricated schema/model or a manual edit to Convex `_generated` files.
- Better Fetch 1.3.1's option/hook declarations now permit explicit undefined on optional properties, matching its own published call signatures and runtime option merging. Required properties and their value types remain unchanged. Compile-time regressions reject a missing/non-string password and an invalid cache mode, and retain generated platform-ID typing.


All patches and their removal conditions need review: remove when compatible upstream declarations pass the same checks. No forced peer dependency, skipped library checking, `any`, ambient fake library module, generated-file substitution or runtime auth patch is used.

The UI/auth compilation retains `strict: true`, `skipLibCheck: false`, `exactOptionalPropertyTypes: true` and the other root safety flags. The final full typecheck passes with these declaration corrections; a diagnostic exact-optional relaxation was not retained. Bun's published declarations are required by Better Auth but conflict with Vite's ImportMeta declarations, so separate UI/server and tooling typecheck projects avoid mixing those globals. A build-owned typed constant carries the two public deployment URLs. The root uses the existing spike's Node 26 declaration version to satisfy Bun; runtime stays Node 24.18.0.

Reproduce the adapter schema declaration generation with the pinned compiler: `pnpm exec tsc --ignoreConfig --strict --exactOptionalPropertyTypes --declaration --emitDeclarationOnly --module esnext --moduleResolution bundler --target es2023 --types node --outDir /tmp/palladian-schema-declarations node_modules/@convex-dev/better-auth/src/component/schema.ts`. Its output is the schema declaration included in the pnpm patch. The component's actual schema source, runtime files and root Convex-generated files are unchanged by this correction.

## A08 recovery and optional TOTP — proposed, not implemented

**Development pilot only: operator reset is the sole recovery option. No real data until P9 implements and tests an accepted recovery design.** No reset backdoor is shipped in P1. An operator can provision another disposable fixture account, but cannot silently transfer a platform identity by email.

Use the pinned library's maintained two-factor plugin and supported Convex component schema, subject to a fresh compatibility proof. Enrollment requires the current password, displays a TOTP secret/QR only in the active account flow, and commits enrollment only after a correct first code. Normal navigation, reading and writing do not prompt for step-up. Removal requires the supported password/factor check. Recovery-code regeneration invalidates previous codes; codes are displayed once, never logged/exported by diagnostics, and only the library's protected server representation is stored. Prove cross-domain pending-challenge persistence, reload, wrong/expired codes, concurrent one-use redemption, replay rejection, and recovery-code exhaustion. Test the actual plugin before adopting it; a supported-plugin listing is not that proof.

For forgotten passwords, prefer the library's one-use, expiring password-reset mechanism with an owner-controlled verified recovery channel. Use generic request responses, library rate limiting, exact trusted callback URLs and no secret-bearing application resource links. A successful reset must revoke **all device sessions**, including still-valid access JWTs through live-session checks. Revoking agent grants is an explicit separate choice. Confirm that the selected library/plugin combination enforces both policies; do not silently inherit different defaults.

**Phrase recovery remains a required reviewer decision.** Library TOTP backup codes are not a phrase-based forgotten-password recovery path, and email-only/operator-only recovery does not satisfy the prior preference. No supported phrase mechanism has been proved in this pinned combination. Proposed review choice: accept a maintained recovery plugin that supports an offline phrase and the above one-use/reset/revocation rules, or explicitly approve a concrete maintained-library design before implementation. Do not invent mnemonic conversion, secret hashing/encryption or a second auth protocol here. If the reviewer wants standard library reset plus backup codes instead, record that as an explicit owner-approved contract change, not an implementer default. Until resolved and tested, A08 and personal-data adoption remain blocked.

P9 acceptance must exercise enrollment, removal, lost-factor recovery, forgotten-password recovery, one-use races, token expiry, all-device revocation, grant preservation/explicit revoke choice, diagnostics redaction, and ordinary navigation without step-up. Recovery never changes stable platform identity.

Primary references: [official React integration](https://labs.convex.dev/better-auth/framework-guides/react), [session policy](https://better-auth.com/docs/concepts/session-management), [supported plugins](https://labs.convex.dev/better-auth/supported-plugins). Implementation behavior was checked against the pinned package source, including `src/react/index.tsx`, `src/plugins/cross-domain/client.ts`, and Better Auth `dist/api/routes/session.mjs`.

## Blocking browser findings and concrete correction proposals

These findings supersede any suggestion that the local transport is proven safe for adoption. The code is a review candidate; **P1 has not passed**.

1. **A07 late sliding response overwrites the next account's credential.** `tests/auth/stale-response.mjs` creates A and B, ages A past the daily threshold through the local admin component API, completes A's `/get-session` on the real server, holds the response before browser processing, signs A out, signs B in successfully, then delivers A's response. The following official-client session check no longer resolves B. The pinned cross-domain `onSuccess` writes `Set-Better-Auth-Cookie` into whatever credential jar exists when the response arrives; it has no request/session-generation check. A's live server session remains revoked; this is not evidence of a server authorization bypass or private A data being returned to B. It is a credential/state regression that can force another login, and it blocks acceptance.

   **Proposed correction, not implemented:** obtain an upstream-compatible adapter fix, or explicitly review a minimal patch to that adapter's request/response storage boundary. Bind each request to the session credential/generation present at dispatch. Ignore obsolete session-cookie/session-state writes and notifications when the current generation differs (including empty after explicit logout), while allowing successful intentional sign-in in its own current generation. Use the existing supported cookie parsing/storage primitives. Do not add rotations, revoke unrelated sessions/grants, change lifetimes or suppress the failing assertion. Verify A→logout, A→B, initial unauthenticated→sign-in, same-session sliding across tabs, and signout response races. A stale network response must never invalidate a newer credential. Review is required before making this runtime lifecycle change.

2. **A03 automatic-resume gate fails locally.** The corrected production-build desktop freeze probe waited beyond the actual 900-second JWT lifetime and Convex's five-second verifier tolerance. Old-token denial passed and thaw caused no navigation, but no token response or distinct unexpired token was observed throughout the full 30-second window. The positive post-resume protected-data assertion was not reached. A prior observer could stop on a late initial response; the final observer removes that ambiguity. Root cause is not isolated: investigate official provider scheduling/connection behavior and this integration with redacted timing evidence, and propose any protected lifecycle correction for review. Do not add custom token refresh calls or weaken the assertion. Real iPhone/PWA behavior is still pending.

**Origin result correction:** the preliminary origin probe failed its OTT-disabled-path assertion, not its callback assertion. An initial interpretation of the unformatted failure line incorrectly described this as callback acceptance. The final isolated run verifies registered authenticated access, hostile custom-credential browser preflight rejection with the session preserved, OTT HTTP 404, and hostile absolute callback rejection specifically with HTTP 403 / `INVALID_CALLBACK_URL`. No callback runtime fix was needed or applied. P0's hostile Node-Origin/custom-header observation and all actual hosted-origin/CSRF/hostname checks remain carried limitations; the local browser result does not close them.

The A07 correction proposal changes a protected implementation boundary and is supplied for independent review. It is not silently applied to make the compatibility gate green.
