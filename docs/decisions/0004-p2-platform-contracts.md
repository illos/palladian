# ADR 0004 — P2 workspace, instance and operation contracts

Status: implementation design approved for bounded work by the independent reviewer; final P2 acceptance pending. Scope is P2 only, following independently accepted P1 at `351cac3`. Development fixtures only; no P3 files/search or fabricated Notes/Recipes content.

A platform user receives one default workspace through a transactional `workspaces.ensure`; the live P1 identity adapter remains authoritative. Workspaces have a title, theme preference and revision. Every instance stores its actual workspace, fixed registered definition, title, lifecycle, metadata revision, preferences version and stable creation ordering. Separate `instancePreferences` rows are actual P2 children with their own workspace, instance and revision, allowing parent-consistency checks even between two owned instances of the same definition.

All public operations derive the current live identity. Central scope helpers fetch the real parent records, compare workspace ownership and child relationships, and check the registered definition and active lifecycle. Foreign/missing/mismatched/archived live targets return the same `NOT_FOUND` code without a title or existence disclosure. Explicit owner-only archive listing and repeated archive are management paths. Existing P1 auth, session and identity lifecycle functions are unchanged.

App endpoints live under fixed build-time Notes/Recipes server modules. They import mandatory scope helpers and bind their permitted definition to the server registry. P2 registers actual read/update operations for instance density preferences. A Notes operation rejects a Recipes instance; no argument selects a table, function path or arbitrary operation. The platform install operation accepts only the two approved definition literals. This is a trusted-code boundary against mistakes, not a sandbox.

Structured updates are semantic. `instances.rename` requires its current metadata revision; workspace theme requires the workspace revision; app `setPreferences` requires the child preference revision and validates the requested preference ID against both stored parent fields. Each revision is a nonnegative safe integer. Preference edits increment the child revision and parent `preferencesVersion` together, independently of instance metadata revision. Archive advances metadata revision and disables all live operations immediately; repeated archive of an already-owned archived instance returns its current state without another change. There is no delete, unarchive or byte cleanup claim in P2.

Create receipts are transactionally indexed by live owner, workspace, fixed per-definition operation and caller key. Authorization occurs before receipt lookup. Keys are bounded ASCII identifiers; a canonical JSON representation of normalized create inputs is the deterministic request fingerprint. Same scoped key and payload returns the same instance ID in its current state; changed payload returns `CONFLICT`. Retries after rename/archive cannot overwrite or resurrect the instance. Different owners, workspaces and fixed Notes/Recipes create operations have independent key scopes. Receipts store the result reference and Convex's implicit `_creationTime` timestamp (no additional retention field) and are retained indefinitely in P2; no unreviewed time-based duplicate window or cleanup job is introduced. Retention/GC is a later explicit contract decision.

Titles are trimmed and bounded to 100 characters. List pages default to 25 and are bounded at 100; cursor length and revision inputs are bounded. Listing uses owner/workspace/lifecycle indexes, never global scans followed by filtering. Domain errors use `ConvexError({code,message})` with the existing bounded public vocabulary and fixed messages. Framework argument validation remains Convex's transport validation; host adapters must map it to the logical client error contract without exposing server internals.

Canonical instance paths are `/w/:workspaceId/a/:instanceId/` and `/a/:instanceId/`. The shared pure path builder escapes each segment. `routes.resolveInstance` fetches the actual active instance and parent ownership and returns the canonical path for either presentation; an optional supplied workspace must match the actual parent. Titles never participate in route identity. Registered resource-type metadata and a pure resource-link builder form the extension seam, but content-resource resolution and search remain unavailable until their actual P3/P4 implementation.

Backend signatures and validators use actual generated Convex IDs. The existing logical SDK brands remain distinct; the parent implements one explicit typed host adaptation from validated/generated entity views into logical client contracts. A client string or brand is never authority.

Implementation and test evidence will be recorded in `docs/reviews/P2-implementation.md`; independent review belongs in `P2-review.md`. D01–D06 apply to real workspace/instance/preference/receipt entities. File-byte lifecycle portions remain P3 and actual app-form/collaboration portions remain P4. Real iPhone and hosted follow-up limitations from P1 remain visible.
