# Note history (port plan A4)

Date: 2026-10-22; review rounds 1–4 on 2026-10-23. Branch `feat/notes-history`, on `main` at `0042ef8` (unchanged since round 3), which contains A2 (note actions), A6 (pins and sort orders) and A3 (editor interactions), all merged and released. History joins A2's action registry. Owner request: the next step of the Deltos feature port ([plan 08](../specs/notes-app/08-deltos-feature-port.md), A4).

One backend change, made in round 4 at the coordinator's direction: `history.restore` takes an optional `account` precondition (below), an equality check against the caller that grants nothing; agents omit it. Otherwise the panel uses the existing `history.list`, `history.read` and `history.restore`, which already require edit access, and `notes.content` for the note as it is now. One fundamentals touch, also round 4 and also directed: `NoteChannel` gains a read-only `collabVersion` getter (the revision the editor has incorporated), like A2's `current()`, with no other change to `channel.ts`. Otherwise no protected area is touched: `cache.ts`, `live.ts`, `binding.ts`, `session.ts`, `logout.ts`, `main.tsx` and `editor.tsx` are unchanged, as are `selectNote`, `makeChannel`, `accessLost` and `openRemote`. **The development deployment does not have the new `account` argument yet** (it serves the files-backend branch's functions), and Convex rejects unknown arguments, so this branch's restores fail against it until its `history.ts` is deployed there. The e2e detects this from the deployment's function list and, only then, removes `account` from restore requests at its WebSocket gate (Evidence).

| Restore      | "Restore this version…" asks inline, then sends `history.restore` with `expectedRevision` = the note's current revision from the live `notes.content` query at the moment of confirming, a fresh `requestId`, and the account it is made in. **Before sending, it waits for this window's own typing** (`versions.ts`, `restoreHold`): if the note is open here, its channel must report "saved" (nothing unsent, nothing in flight, no failure), and this window must know of no unsent edits journaled for it. Differences from plan 08 A4, deliberately:

- **Word diff, not character diff.** The plan calls Deltos's diff a character diff, but `lib/textDiff.ts` compares words and whitespace; Deltos's only character-level code is `computeCharDelta`, a "+120 −18" counter stored with its per-device snapshots. The word diff is ported. The counter is not: Palladian's list would need every version's text to compute it.
- **Deltos's 2,000-word cut is not ported.** Deltos truncated both texts at 2,000 tokens and silently dropped the rest from the comparison. The bounded fallbacks above replace it.
- **A "Version" view beside the two comparisons.** Deltos showed only the diff. The plan asks for the version rendered read-only and a diff toggle, so the toggle has three positions: Version, vs Previous, vs Current (Deltos's labels).
- **"Previous" is the version's own starting revision**, not the row below it in the loaded list, so it is exact on page boundaries and for versions that interleave with other people's.
- **Inline confirmation** instead of Deltos's separate confirm screen or a browser `confirm()`, so the version stays visible while confirming.
- **Styles in `history.css`**, loaded with the panel like `appearance.css`, rather than in `styles.css`. It follows `styles.css`'s variables and patterns and stays out of the A3 and A6 branches' changes to `styles.css`.

## For the owner to confirm: restore records and D28

D28 covers cached notes and attachments on a device. The restore records are a minimal safety record kept beside that cache, proposed as an explicit exception:

- **What:** per unresolved or just-applied restore, the account ID, note ID, the revision restored, the expected revision, the request ID, the restored version's end time and two timestamps. No note text, titles or content.
- **Why:** without it, a reload or another window could allow typing that a pending restore would then discard, or replay a restore under another account.
- **Retention:** until the restore's outcome is known (applied ones for 10 more minutes); at sign-out it is settled first if the server is reachable, otherwise kept for that account only. At most 20. Unreadable entries are kept until the person discards them.

## Found during this work (not changed)

- **A restore, or an agent's whole-note edit, discards other devices' unsent typing.** `history.restore` commits one step that replaces the whole document. A device that has typing not yet confirmed when that step arrives rebases its unconfirmed steps over it; steps inside the replaced range map to nothing and are dropped, from the editor and from its journal, and they were never on the server, so they are not in History either. The e2e shows it deterministically: Cy's push is held, he types "word2", Ada restores, and once the restore reaches him "word2" is gone and appears in no revision, while "word1", saved before, is in History. Reading the code confirms the same for agents: MCP `edit_note` with `replace_all` builds the same single whole-document `ReplaceStep` (`notes-core` `edits.ts`, `replaceRange(tr, 0, doc.content.size, …)`), MCP `restore_revision` calls `history.restore`, and `replace_block` or `delete_block` drop unsent typing inside that one block in the same way. The same holds for another tab of the same browser, even once that tab has journaled the typing: cache notifications reach only the store instance that made them, so the restoring tab neither sees the journal nor holds Restore (round 2; e2e step "known gap, not changed (R2-4)"). The guard does catch it if the restoring tab happens to re-read its cache after the other tab journaled; in one round-3 run the server's delayed summary refresh (2 s after an edit) did exactly that and Restore stayed disabled. So the other-tab case is sometimes caught, never reliably; the regression waits for that refresh before the other tab types, to pin the condition the reviewer found. Restores themselves are now shared between tabs (round 3): a tab holds a note that another tab of this browser is restoring. This is collaboration behaviour in the fundamentals (`channel.ts`, the cache's notifications and prosemirror-collab rebasing), raised for the owner with a separately reviewed preservation follow-up; this branch protects only the restoring window.
- **Downgrading an open note's editor to read closes the note for them.** The editor's step subscription is refused, the channel reports access lost, and `accessLost` closes the note with "You no longer have access to that note." and revokes its cached copy, although the person may still read it; the note stays in their list as shared with them. This is channel and `accessLost` behaviour (fundamentals). The e2e's downgrade step checks only that History closes and the server refuses it.
- **The existing `Modal` in `panels.tsx` closes when its padding is clicked.** It treats any click whose target is the `<dialog>` as a backdrop click, and its padding belongs to the dialog. The History dialog has no padding to avoid this; the other dialogs are unchanged.
- **`PanelBoundary` draws its failure box outside the dialog.** If a History query fails because access just dropped, the box can show for a moment before the panel closes.
- **A restore can wait behind continuous typing.** `history.restore` refuses when any edit lands between reading the current revision and the server applying the restore. Before round 1, with timed typing against the remote dev deployment, a collaborator committing a word every quarter second refused 9 and then 20 attempts in a row, and at a word a second 1 to 6 attempts were refused before one landed. This is the `expectedRevision` contract working, and the panel says so each time, but a person typing without pause can hold off a restore. Accepting a restore over edits made after the person confirmed would be a backend contract change, so it is left for review. The e2e now forces one refusal deterministically instead of relying on timing.
- **`live-e2e.mjs`'s `typeAtEnd` helper can type at the start of the note.** It sets the DOM selection with a `Range` and types at once; in one of this branch's e2e runs, before the editor had taken up that selection, " Cy was here." landed before "Recipe", so the title changed and the History dialog's name with it. `history-e2e.mjs` now clicks into the last block, presses Ctrl+End and waits a frame, and checks the title after the setup edits. `live-e2e.mjs` is unchanged.
- (Resolved by A2 as merged: before the rebase, an open note kept the role it opened with, and its journaled row counted as a local draft with no actions. A2's `openTarget` and `isLocalNoteId` now handle both.)
