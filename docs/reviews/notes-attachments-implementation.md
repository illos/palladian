## Design and rules

### Uploads are marks, not content

- **Marks.** A plugin keeps one mark per unfinished upload: a position between blocks, mapped through every transaction (typing, Enter, deletions, undo, a collaborator's steps rebased by prosemirror-collab). The marks are drawn as widget decorations; a transaction that only adds or removes marks changes nothing in the note, so there is nothing to send, journal or show a collaborator.
- **Where an upload lands.** Before an empty block or a block the caret is at the start of, otherwise after the caret's block (`uploadPoint`). Inside a list item it lands after the item's paragraph. Never before the first line, which is the note's title (D46, D80): a caret in an empty title puts the upload after it. A selected image or file: after it. A drop: at the drop point by the same rule. A paste first deletes a non-empty selection, as a paste does.
- **Landing.** `insertUpload` inserts the node where the mark is now (`insertPoint`; if edits have put the mark inside a line, the line is split there), assigns block IDs in the same transaction, and closes the undo group first, so Undo removes the attachment on its own. The mark goes with it.
- **Order.** Each upload has a start order. When one lands, marks of uploads begun later at the same place move after it and earlier ones stay before it, so files chosen together land in the order chosen whichever finishes first.
- **Rechecks at landing.** The node is inserted only if files are still on, the note is still editable, and the note stays within 200 attachments (the server's per-revision limit, which would otherwise refuse the push and block the note). Otherwise the upload fails with a message and keeps its widget; Retry tries again.

### The upload pipeline (B1's protocol)

1. Refused at once, with Remove only: an empty file, or one over 25 MB.
2. SHA-256 of the file, then `files.createUpload` with the server ID of the note and a `requestId` fixed for this upload. A new note not yet created on the server is waited for, up to 15 seconds.
3. `PUT /files/upload/<objectId>` with the ticket in the Authorization header, through XMLHttpRequest for upload progress. The Worker checks and finalizes.
4. The file's own bytes go into the cache (typed as the picture or as a download), so the picture shows at once without reading it back.
5. Two uploads run at a time; the rest wait.

**Waiting for admission (review round 1, F7).** An upload waits 30 seconds for `files.createUpload`, then fails with Retry and Remove. It keeps the admission itself, which may still answer: then Remove can release that object, and Retry asks again with the same `requestId` (the same object). An admission that answers after its upload was removed, after the note closed, or after the upload started a new request is released through the service, and so the account, it came from. An object that landed in the note is never released.

**Files turned off (round 3, R3-3).** Every unfinished upload stops at once: its request is aborted, the object it made is released (an admission that answers later is released through the service that made it), and its widget says "Files were turned off on the server." with Remove only. The gate is checked again before asking the server, before the transfer, before keeping the bytes and before inserting, and no upload starts while files are off. Once they are on again, Retry starts a new upload (the old object was released).

**Retry** runs the same pipeline with the same `requestId`: the server answers with the same object (a fresh ticket while pending, or "ready"), so a retry never makes a second object (spec 02). When the object is gone or its ticket expired (404, 410, or a failed replay), the retry starts a new request. **Cancel** and **Remove** abort the request and call `files.cancelUpload` for any object made: a pending object fails, a ready one no note uses is deleted, and its bytes are tombstoned (B1).

Messages: the server's own refusal text (for example "Too many uploads are in progress. Wait for some to finish." or "Restore this note from Trash before adding files."), or the upload failed / expired / took too long / changed while sent / files are off, by the Worker's status. No ticket, token, URL or file name is logged.

### Closing the note mid-upload

Closing the note (opening another, signing out, the editor being replaced) **cancels its unfinished uploads**: requests are aborted and `files.cancelUpload` is asked for each object made. Nothing lands later, and reopening the note shows no widgets. A failed upload's widget is dropped the same way. If the page itself goes away, the server's sweeps finish the job: pending uploads expire after an hour and never-referenced objects are removed after seven days (B1). Keeping uploads alive across notes would mean inserting into a note with no editor open, which only the channel (fundamentals) can do.

### Showing attachments

- **One runtime per editor** (`AttachmentRuntime`) tracks every object its node views show: loading, shown, offline, unavailable or failed. Whether a view wants an object's bytes is recorded apart from its availability, so a picture that becomes available loads at once (review round 1, F5).
- **Fenced reads (F3).** A read of bytes, for a picture or a download, counts only while its editor is open, for the account and session generation it began under, while files are on (round 3), and while the server still lists the object for the note, checked again once the bytes arrive. Otherwise it is aborted and changes nothing: no picture, no cache entry, no download. Closing the editor, a new session generation or files turning off aborts pending reads and downloads; an object the server stops listing has its pending read aborted. The lightbox closes when its picture becomes unavailable, when the session generation changes and when the editor closes.
- **Reconciling (F6).** What each object may show is rechecked whenever the server's list arrives, and whenever the document or its unsent steps change, acknowledgements included: provisional display of an object our own unsent change brought in ends once that change is acknowledged and the server's list still lacks the object.
- **Bytes**: this page's memory cache first; otherwise read through the Worker and kept in memory. Without a connection and without cached bytes, a picture shows "Not available offline"; a failed read shows "The picture could not load." with Retry.
- **Availability**: the runtime follows `files.noteObjects` for the open note. An object the server does not list, and that no unsent local step brings in, is unavailable; so is one the Worker answers with 404 under the same condition. Unavailable wins over cached bytes, and those bytes are dropped. While our own unsent change brings an object in (a paste from another note, before the server has accepted it), a 404 waits for the server's next list instead of showing unavailable.
- **Legacy sources** (`attachment:` text that names no object, B2 review F7) show as unavailable.
- **Web images** (`https:`) render as before, with the same resize grip and lightbox.
- **Taps.** In an editable note the first tap selects an image or chip (so it can be resized, copied, cut or deleted, as before B3), and a tap on the selected one opens it. In a read-only note one tap opens it. This follows A3's links (Open, Edit and Remove in an editable note; open directly when read-only).
- **Files off (round 2, R2-2).** While `files.capabilities` is not on, the editor has no attachment node views: images and file blocks render through the schema's own `toDOM`, exactly as on `main` (`<img src=… contenteditable="false" draggable="true">`, a file block as its name), with `main`'s click and key behaviour and no reads, focus targets, lightbox or resizing. When the gate turns on or off, the node views are swapped with `setProps`; ProseMirror redraws the document and keeps the state, selection and history. The runtime follows the note's objects only while files are on, and an open lightbox closes when they turn off.
- **Keyboard (F8).** A shown picture is a focusable control ("View picture: <description>") and a file chip one too ("Download <name>, <type>, <size>", or "Open …" once a reader is registered for its type); Enter or Space opens them. In an editable note with files on, a selected or focused picture shows a labelled "Picture size" group (Smaller, Larger, Natural size), and on the focused picture -, + and 0 do the same. A step is a fifth of the width, within the drag's limits. The node views keep these keys from the editor, and pointer taps still select first.
- **Resize.** The grip shows on hover with a mouse and on the selected image. The picture follows the pointer; the note changes once, on release, with `setNodeAttribute(width)`, clamped between 48 px (32 px minimum) and the smallest of the picture's natural width, the column and 4,096 px. Double-click resets to natural size. The grip is absent while files are off (a width is a file feature the server would refuse), in read-only notes, and until the picture has loaded.
- **Lightbox.** A modal `<dialog>` portalled to the body: Escape (the dialog's cancel), a click on the backdrop or the space around the picture (click, not pointerdown: Deltos GOTCHA-0018), or × close it.
- **Downloads** use a `blob:` URL typed `application/octet-stream` and the `download` attribute, revoked after a minute.
- **B4 seam.** `registerFileOpener("application/pdf", open)` makes a media type open instead of download; the opener gets the file's attributes and a function that returns its bytes through the cache, fenced like a download.

### Reads, tokens and what the page holds

- **The token.** The live service asks the Better Auth client for a Convex token (`auth.convex.token()`, as `live.ts` does), keeps it only if its `sub` is this account and the account is still signed in to the server, and reuses it until a minute before it expires. A 401 asks for a new one once (Deltos GOTCHA-0006).
- **The request.** `fetch` with the token in the Authorization header, `cache: "no-store"`, `credentials: "omit"` and `referrerPolicy: "no-referrer"`. Note and object IDs are checked against the Worker's own pattern before they become a path.
- **What the page holds.** Bytes reach the page only as `blob:` URLs typed as one of the four inline picture types or `application/octet-stream`, so a file's bytes are never rendered as HTML or SVG in the app's origin (Deltos #694). Upload tickets travel only in the PUT's header. The service worker passes requests with an Authorization header through untouched. No token, ticket or signed URL is in the DOM, a log or Git; the e2e checks the page and the read URLs for tokens.

### The byte cache (memory only)

- **Memory only (round 3).** `attachment-cache.ts` keeps bytes in this page's memory and nowhere else: no IndexedDB, localStorage or other storage that outlives the page. A reload starts empty; a cached note opened offline shows "Not available offline" for its pictures until the Worker can be reached. No offline downloads either way (D84).
- **Cap: 64 MB**, least recently used first; an entry larger than an upload can be (25 MB) is never kept.
- **One scope.** Bytes belong to one account and session generation (`follow`). Reads and stores need a ticket taken for the current scope; every clear ends every ticket. The same page going from Ada to Bob and back to Ada (three session generations) never sees Ada's earlier bytes, and a read begun in an earlier scope neither reads nor stores.
- **What fills it**: only bytes shown or downloaded while files are on, and the bytes of the person's own uploads.

### Clearing (D28)

`App.tsx` follows the session synchronously (`session.subscribe`, outside the fundamental functions): whenever the session's account or generation changes, or it is signed out or revoked, the cache follows the new scope, or none, and every byte is dropped inside the session's own update, before anything can read again. Another tab's sign-out or account cleanup reaches this page's session (its existing adoption through the store's clear events and the account hint), so it clears here too. Turning files off clears the cache as well. Nothing needs clearing at the next start, because nothing was stored. The connect, invitation and reset pages show no attachments and keep no bytes.

## Persistent byte cache (proposal, needs owner approval)

**Proposal.** Keep attachment bytes in the notes cache's own per-account database in `cache.ts`: one more table of bytes (and sizes) keyed by account and object, deleted in `deleteAccountData` with the account's notes, written only through the store's existing epoch and activation fences, and read only for an allowed account. The tested account lifecycle (sign-out, revocation, switching, clears across tabs, clears a closed tab left unfinished, re-activation after a clear) then covers the bytes with no second mechanism. It changes the cache schema and `cache.ts`, so it needs the owner's approval and protected-core review, as A6's store did.

**Why a separate store cannot be made safe cheaply.** Rounds 1 to 3 found, in turn, that a store beside the notes cache must re-create that lifecycle itself, and each attempt left a gap:

- R1-F1: its cleanup ran only where the app was mounted, not on the other pages that own a session.
- R1-F2: clears that failed or were cut short left readable bytes; separate transactions left bytes without size records.
- R2-1: when IndexedDB could not record the clear, the intent could be lost and old bytes became readable after the same account signed in again.
- R3-1: the cross-tab cleanup list lost entries when two tabs rewrote it.
- R3-2: a read delayed across a clear, in another tab or in the same tab after Ada → Bob → Ada, returned old bytes.
- R3-4: a malformed list either allowed reads or disabled the cache for good.

The notes cache already solves these with locks, epochs, a persisted clear state and activation fences; sharing them is the cheap, correct route.

**Until then**, cached notes opened offline show their pictures as "Not available offline", and every page load reads pictures again through the Worker.

## Differences from plan B3, deliberately

- **The first tap selects** an image or chip in an editable note; a tap on the selected one opens it. The plan says a tap opens the lightbox or downloads. On a phone, tapping is the only way to select an attachment to resize, copy, cut or delete it, and B1's gate behaviour (refusing a cut, keeping copies) depends on selecting it. Read-only notes open on the first tap, as the plan says. This matches A3's links.
- **Retry only when it can help.** An empty file, one over 25 MB, or a note already holding 200 attachments fails with Remove only.
- **Closing the note cancels its uploads** (the plan does not say).
- **Web images get the lightbox and resizing too**, under the same files gate.
- **Uploads into a new note wait** up to 15 seconds for the server to create it, then fail with Retry.
- **Copied text with a picture of it** (some apps put both on the clipboard) pastes as text; a picture alone, or files, upload.
- **"Oldest-first" is least recently used**, as in Deltos's CONV-0007.
- **Bytes are cached in memory only**, not in IndexedDB, until the persistent cache is approved (round 3 decision); cached notes show their pictures offline only within the same page.

## Proposal touching the fundamentals (not made)

**Name the source of pasted attachments in pushes.** B1 records a new reference only with a proof. Its report expected "B3 passes the source of a paste" as `sourceNoteIds`, which `notes.push` already accepts. The push is sent by `channel.ts` through `live.ts`'s transport, both fundamentals, so B3 does not send it.

**Why it blocks turning files on (review round 1, F4).** Without a named source, a copy between notes relies on the server's bounded search: 48 reference rows for the whole change. The reviewer's convex-test probe copied 49 attachments from a readable shared note, each with one reference: only 48 were proven, and the 49th stays in the document granting nothing and keeping nothing alive. Naming the source proved all 49. Ordinary multi-file copies are affected, not only popular objects. **So B3 can ship with the files gate off, but files must not be turned on until this change is approved and built.**

Concrete change, for review as collaborative persistence:

1. **Clipboard.** The editor's copy marks Palladian HTML with the note it came from (`data-source-note` on the slice wrapper, from the attachments context).
2. **Transaction.** On paste, when the slice brings in attachments the note lacks, the editor records `{ sourceNoteId, objectIds }` in a transaction meta.
3. **Journal and channel.** `NoteChannel` keeps, with each unsent step, the sources that step needs, in memory and in the draft journal record, so they survive a reload. Rebasing over others' steps keeps them with the step's rebased form. A retry after a lost answer resends them. They are dropped only when the step is acknowledged, never before.
4. **More than three sources.** `notes.push` accepts at most three. A paste comes from one note, so each step needs at most one source; when the unsent steps together need more than three, the channel sends them in consecutive pushes whose steps need at most three, and never drops a needed source.
5. **Tests.** Channel unit tests asserting the push arguments through acknowledgement, a retry after a lost answer, a reload from the journal and a rebase; a batch split at four sources; an e2e copying 49 attachments from one note and attachments from four notes, every reference proven.

## Found during this work (not changed)

1. **History previews** render attachments through `DOMSerializer`: an `attachment:` image is a broken `<img src="attachment:…">` and a file block is its name. A follow-up can draw them with these node views, read-only, reading through `/files/notes/<noteId>/<objectId>` (editors may read objects from earlier revisions).
2. **Public pages** have no app view yet. When they do, they should read `/files/public/<token>/<objectId>`.
3. **Dropping a file on the editor while files are off** is left to the browser (the brief keeps today's behaviour). ProseMirror marks the editor as a drop target and does not handle file drops, so browsers open the dropped file in the tab. Not checked on a device; a follow-up could cancel such drops.
