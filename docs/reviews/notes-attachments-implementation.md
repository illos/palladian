# Inline attachments (port plan B3)

Date: 2026-10-23. Branch `feat/notes-attachments`, based on `main` at `8e7088a`, which contains B1+B2 (the files backend, released with file writes off), A2–A6 and their releases. Plan: [08](../specs/notes-app/08-deltos-feature-port.md), Track B, B3. B4 (file notes and the PDF reader) and B5 (the Deltos bytes) follow.

B3 is client work on B1's protocol. **No backend, Worker or notes-core change**, so nothing was pushed to the dev deployment. **The fundamentals are untouched**: `cache.ts`, `live.ts`, `channel.ts`, `binding.ts`, `session.ts`, `logout.ts` and `main.tsx` are as on `main`, and in `App.tsx` `selectNote`, `makeChannel`, `accessLost` and `openRemote` are unchanged. The byte cache is cleared at sign-out through existing observables (the session snapshot and the notes cache's invalidation events), so it ships enabled; no fundamentals change was needed for it. One proposal touching the fundamentals (naming the source of pasted attachments) is below; it is not needed for B3 to work. Nothing was deployed.

## Design and rules

### Uploads are marks, not content

- **Marks.** A plugin keeps one mark per unfinished upload: a position between blocks, mapped through every transaction (typing, Enter, deletions, undo, a collaborator's steps rebased by prosemirror-collab). The marks are drawn as widget decorations; a transaction that only adds or removes marks changes nothing in the note, so there is nothing to send, journal or show a collaborator.
- **Where an upload lands.** Before an empty block or a block the caret is at the start of, otherwise after the caret's block (`uploadPoint`). Inside a list item it lands after the item's paragraph. Never before the first line, which is the note's title (D46, D80): a caret in an empty title puts the upload after it. A selected image or file: after it. A drop: at the drop point by the same rule. A paste first deletes a non-empty selection, as a paste does.
- **Landing.** `insertUpload` inserts the node where the mark is now (`insertPoint`; if edits have put the mark inside a line, the line is split there), assigns block IDs in the same transaction, and closes the undo group first, so Undo removes the attachment on its own. The mark goes with it.
- **Order.** Each upload has a start order. When one lands, marks of uploads begun later at the same place move after it and earlier ones stay before it, so files chosen together land in the order chosen whichever finishes first.
- **Rechecks at landing.** The node is inserted only if files are still on, the note is still editable, and the note stays within 200 attachments (the server's per-revision limit, which would otherwise refuse the push and block the note). Otherwise the upload fails with a message and keeps its widget; Retry tries again.

### The upload pipeline (B1's protocol)

1. Refused at once, with Remove only: an empty file, or one over 25 MB.
2. SHA-256 of the file, then `files.createUpload` with the server ID of the note and a `requestId` fixed for this upload. A new note not yet created on the server is waited for, up to 15 seconds.
3. `PUT /files/upload/<objectId>` with the ticket in the Authorization header, through XMLHttpRequest for upload progress. The Worker checks and finalizes.
4. The file's own bytes go into the cache (typed as the picture or as a download), so the picture shows at once without reading it back.
5. Two uploads run at a time; the rest wait.

**Retry** runs the same pipeline with the same `requestId`: the server answers with the same object (a fresh ticket while pending, or "ready"), so a retry never makes a second object (spec 02). When the object is gone or its ticket expired (404, 410, or a failed replay), the retry starts a new request. **Cancel** and **Remove** abort the request and call `files.cancelUpload` for any object made: a pending object fails, a ready one no note uses is deleted, and its bytes are tombstoned (B1).

Messages: the server's own refusal text (for example "Too many uploads are in progress. Wait for some to finish." or "Restore this note from Trash before adding files."), or the upload failed / expired / took too long / changed while sent / files are off, by the Worker's status. No ticket, token, URL or file name is logged.

### Closing the note mid-upload

Closing the note (opening another, signing out, the editor being replaced) **cancels its unfinished uploads**: requests are aborted and `files.cancelUpload` is asked for each object made. Nothing lands later, and reopening the note shows no widgets. A failed upload's widget is dropped the same way. If the page itself goes away, the server's sweeps finish the job: pending uploads expire after an hour and never-referenced objects are removed after seven days (B1). Keeping uploads alive across notes would mean inserting into a note with no editor open, which only the channel (fundamentals) can do.

### Showing attachments

- **One runtime per editor** (`AttachmentRuntime`) tracks every object its node views show: loading, shown, offline, unavailable or failed.
- **Bytes**: the cache first (memory, then IndexedDB); otherwise read through the Worker and cached. Without a connection and without cached bytes, a picture shows "Not available offline"; a failed read shows "The picture could not load." with Retry.
- **Availability**: the runtime follows `files.noteObjects` for the open note. An object the server does not list, and that no unsent local step brings in, is unavailable; so is one the Worker answers with 404 under the same condition. Unavailable wins over cached bytes, and those bytes are dropped. While our own unsent change brings an object in (a paste from another note, before the server has accepted it), a 404 waits for the server's next list instead of showing unavailable.
- **Legacy sources** (`attachment:` text that names no object, B2 review F7) show as unavailable.
- **Web images** (`https:`) render as before, with the same resize grip and lightbox.
- **Taps.** In an editable note the first tap selects an image or chip (so it can be resized, copied, cut or deleted, as before B3), and a tap on the selected one opens it. In a read-only note one tap opens it. This follows A3's links (Open, Edit and Remove in an editable note; open directly when read-only).
- **Resize.** The grip shows on hover with a mouse and on the selected image. The picture follows the pointer; the note changes once, on release, with `setNodeAttribute(width)`, clamped between 48 px (32 px minimum) and the smallest of the picture's natural width, the column and 4,096 px. Double-click resets to natural size. The grip is absent while files are off (a width is a file feature the server would refuse), in read-only notes, and until the picture has loaded.
- **Lightbox.** A modal `<dialog>` portalled to the body: Escape (the dialog's cancel), a click on the backdrop or the space around the picture (click, not pointerdown: Deltos GOTCHA-0018), or × close it.
- **Downloads** use a `blob:` URL typed `application/octet-stream` and the `download` attribute, revoked after a minute.
- **B4 seam.** `registerFileOpener("application/pdf", open)` makes a media type open instead of download; the opener gets the file's attributes and a function that returns its bytes through the cache.

### Reads, tokens and what the page holds

- **The token.** The live service asks the Better Auth client for a Convex token (`auth.convex.token()`, as `live.ts` does), keeps it only if its `sub` is this account and the account is still signed in to the server, and reuses it until a minute before it expires. A 401 asks for a new one once (Deltos GOTCHA-0006).
- **The request.** `fetch` with the token in the Authorization header, `cache: "no-store"`, `credentials: "omit"` and `referrerPolicy: "no-referrer"`. Note and object IDs are checked against the Worker's own pattern before they become a path.
- **What the page holds.** Bytes reach the page only as `blob:` URLs typed as one of the four inline picture types or `application/octet-stream`, so a file's bytes are never rendered as HTML or SVG in the app's origin (Deltos #694). Upload tickets travel only in the PUT's header. The service worker passes requests with an Authorization header through untouched. No token, ticket or signed URL is in the DOM, a log or Git; the e2e checks the page and the read URLs for tokens.

### The byte cache

- **Shape.** A separate IndexedDB database, `palladian-attachments`, in its own module, with two tables keyed by `[accountId+objectId]`: `entries` (size and last use) and `bytes` (the Blob). Eviction reads only `entries`, never the bytes.
- **Cap: 200 MB per device**, Deltos's CONV-0007 budget. Eviction is least recently used first: a read marks an entry used. Entries over 25 MB (larger than any upload) are not kept. A small memory tier (48 MB) keeps redrawn pictures from waiting. If IndexedDB fails, the cache works in memory only.
- **What fills it**: only bytes shown or downloaded, and the bytes of the person's own uploads. Nothing is fetched ahead and there is no offline-download feature (D84). A picture shown before can show again offline, as cached notes do.
- **One account at a time.** `retain(accountId)` names the only account whose bytes may be read or stored and deletes every other account's. `forget(accountId)` deletes one account's bytes. Each clear bumps the account's mark: a fetch started before it stores nothing, and a write already under way when a clear starts is removed again.

### Clearing at sign-out (D28)

`App.tsx` (outside the fundamental functions) does two things:

1. `retain(permitted ? accountId : null)` whenever the session snapshot's account or permission changes. Bytes are kept exactly for the account whose cached notes the app may show, by the same `permitted` rule.
2. On the notes cache's `{ accountId, invalidated: true }` event (`store.subscribe`, already used by `App.tsx`), `forget(accountId)`. The store emits it when any clear of that account starts in this tab (`clearAccount`), and when another tab's clear arrives (its BroadcastChannel message).

| Event                                  | What clears the bytes                                                                                                                              |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sign-out                               | The snapshot turns `signed-out` with no account: `retain(null)`; then `clearAccount` emits the invalidation: `forget`                              |
| Revoked session                        | The snapshot turns `revoked`: `retain(null)`; `clearAccount`: `forget`                                                                             |
| Switching accounts                     | The old account's cleanup sets the snapshot's account to null (`retain(null)`), the clear emits `forget`, and the new account is retained on ready |
| Another tab signs out                  | Its clear reaches this tab's store: `forget`; this tab's session adopts the sign-out: `retain(null)`                                               |
| A clear interrupted by closing the app | The next start is signed out (the hint records sign-out before clearing) or signed in as someone else: `retain` deletes the rest                   |
| Session expired (not signed out)       | Nothing, as for the notes cache: the account stays shown                                                                                           |

No fundamentals file changed. Because the clear is driven by those observables rather than inside `clearAccount`'s transaction, the bytes are cleared when the clear starts, not atomically with the notes; the interrupted-clear row covers the gap.

## Differences from plan B3, deliberately

- **The first tap selects** an image or chip in an editable note; a tap on the selected one opens it. The plan says a tap opens the lightbox or downloads. On a phone, tapping is the only way to select an attachment to resize, copy, cut or delete it, and B1's gate behaviour (refusing a cut, keeping copies) depends on selecting it. Read-only notes open on the first tap, as the plan says. This matches A3's links.
- **Retry only when it can help.** An empty file, one over 25 MB, or a note already holding 200 attachments fails with Remove only.
- **Closing the note cancels its uploads** (the plan does not say).
- **Web images get the lightbox and resizing too**, under the same files gate.
- **Uploads into a new note wait** up to 15 seconds for the server to create it, then fail with Retry.
- **Copied text with a picture of it** (some apps put both on the clipboard) pastes as text; a picture alone, or files, upload.
- **"Oldest-first" is least recently used**, as in Deltos's CONV-0007.

## Proposal touching the fundamentals (not made)

**Name the source of pasted attachments in pushes.** B1 records a new reference only with a proof. Its report expected "B3 passes the source of a paste" as `sourceNoteIds`, which `notes.push` already accepts. The push is sent by `channel.ts` through `live.ts`'s transport, both fundamentals, so B3 does not send it.

Today a copy between notes relies on the server's bounded search: up to 48 reference rows, all of them for a single copied object. That proves access for ordinary copies; the browser and e2e runs show it. An object with very many references, copied without its source named, records an unproven reference: it shows "Attachment unavailable" to everyone and keeps nothing alive.

Concrete change, for review as collaborative persistence:

1. The editor's copy marks Palladian HTML with the note it came from (`data-source-note`, from the attachments context).
2. On paste, when the slice brings in attachments the note lacks, the editor sets a transaction meta `{ sourceNoteId }`.
3. `NoteChannel` keeps the source IDs of unsent steps (with the steps, in memory and in the draft journal record) and sends at most three with the next `notes.push`; the transport passes them through. The server needs no change.
4. Tests: a channel unit test asserting the push arguments, including after a reload from the journal; an e2e copy of an object with more than 48 references.

## Found during this work (not changed)

1. **History previews** render attachments through `DOMSerializer`: an `attachment:` image is a broken `<img src="attachment:…">` and a file block is its name. A follow-up can draw them with these node views, read-only, reading through `/files/notes/<noteId>/<objectId>` (editors may read objects from earlier revisions).
2. **Public pages** have no app view yet. When they do, they should read `/files/public/<token>/<objectId>`.
3. **Dropping a file on the editor while files are off** is left to the browser (the brief keeps today's behaviour). ProseMirror marks the editor as a drop target and does not handle file drops, so browsers open the dropped file in the tab. Not checked on a device; a follow-up could cancel such drops.
4. **A files-gate browser test passed on the phone project by accident.** In "R5-2: … cutting an attachment is refused…", deleting the file left the image after it selected, and typing straight after the tap on the title replaced that image (Chromium's tap reaches ProseMirror through an asynchronous `selectionchange`). The assertion `toContainText("Album typed")` still passed because the images contribute no text. B3's placeholder text exposed it. Checked on a temporary checkout of `main`: the same happens there. The test now waits until the tap has moved the selection, as its `pasteAtEnd` helper already did, and also asserts the title itself. Its five `img[src^="attachment:"]` selectors now name the node view (`.note-image[data-src^="attachment:"]`); left as they were they would match nothing and pass vacuously.
5. **Bytes of objects from a note the person later loses access to** stay cached until sign-out or eviction. They cannot be shown through that note any more (its cached copy is gone). Online, the server's list decides for any other note that references them. Offline, a note the person can still open that references the same object shows the cached bytes. The cache is keyed by object, not note; indexing it by note would allow dropping them with the note.
6. **iOS Scan Documents.** Deltos DEC-0008 found that current iOS's web file picker does not offer Scan Documents; it lives in the Files app. The input keeps every source iOS offers. Whether Scan Documents is among them is for the iPhone check.
7. **`wrangler dev` needs `apps/notes/dist`** to exist (the Worker's assets). The e2e creates an empty one if missing and removes it after.
