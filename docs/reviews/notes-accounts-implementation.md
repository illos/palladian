# Notes accounts — sign-in, passkeys, password reset and account email

Date: 2026-10-18. Branch `feat/notes-accounts`. Owner request: "we need a proper login and signup flow", with decisions D95–D99 (invite-only stays; passkeys in v1; email from notes@parabolic.studio; a password reset wipes other devices; the app moves to notes.parabolic.studio). Independent reviews are recorded separately (`notes-accounts-round1-astra-review.md`, `notes-accounts-round2-astra-review.md`).

| Sign-in after a reset                           | A password sign-in that verified the old password just before a reset cannot get a session: the `session.create.before` hook (`auth.ts`) reads the reset count first, then verifies the password again against the current credential, and the session records that count (`credentialEpoch`); a Convex trigger in the transaction that writes the session refuses it if the count has moved.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Devices after a reset (D98)                     | Each browser holds a random device secret (`palladian.notes.device.v1`); the server keeps only its hash in `devices`, per account, with the reset count (`principals.resetEpoch`) the browser last caught up with. `finishReset` moves the resetting browser's record to the new count in the reset transaction, so it never falls behind (all its tabs share the secret). A session check asks `devices.status(secret)`, which only the secret's holder can ask. With a live session, a browser new to the account is bound before it opens (so its copies always postdate the binding), and a browser behind the count is bound and reported **revoked**, so copies from before a reset are cleared even if the person signed in again first. With no session, it is revoked only on the server's answer for the account it shows, and only if no sign-in or sign-out happened meanwhile in any tab. A failed question is transient. Revocation runs the existing cleanup (account hidden, copies and drafts cleared, no export); an interrupted clear resumes after reload. |
| Sign-in races                                   | A passkey ceremony is bound to the sign-in state it began in (`sign-in-flow.ts`): the session generation, the cross-domain intent counter and the stored session token. Another sign-in or sign-out (same tab, other tab, or a newer session decision) cancels the browser prompt and refuses the verification before any session is stored (abort signal linked to the cross-domain request guard, plus a check immediately before the verification request). A dead token being cleared is not a new sign-in. Automatic sign-in after a reset or account creation runs only if the same state still holds and never throws; otherwise the page reports the completed reset or account and links to sign-in.                                                                                                                                                                                                                                                                                                                                                                  |

## Protected areas touched

- **Auth storage**: the Better Auth component moves from the npm default to a local install, same name and tables, plus the passkey table and an optional `session.credentialEpoch`. Rehearsed on the cloud dev deployment: an account and a live session created on the old component were valid after the push. The existing backend tests pass against the local component.
- **Auth configuration** (`convex/auth.ts`): passkey plugin; reset lifecycle and `/reset-password` disabled; a session `create.before` hook and a session trigger.
- **Session lifecycle** (`apps/notes/src/session.ts`): `settled()` and the account passed to `check`; `auth-service.ts` may return `revoked` from server device records.
- **Agent connections**: `connections.disconnectAgents`, called only inside the reset transaction with the person's explicit choice. Notebook memberships are untouched.
- **Hostname**: the relay accepts links only for `PUBLIC_ORIGIN` paths `/reset#` and `/invite#`; the production origin moves to `notes.parabolic.studio`.

## Known limits and pending work

- **Sender domain.** parabolic.studio was onboarded by the owner on 2026-10-18 (records on `cf-bounce.parabolic.studio`, DKIM, and `_dmarc` with `p=reject`; the apex MX used by Email Routing is unchanged). Delivery is proven only once production sends a real message. Cloudflare Email Sending is in public beta.
- **Revocation needs a session check.** A device learns of a reset only when it next checks its session with the server; a device that stays offline keeps its copies until then, as the spec states.
- **No caches predate the device records.** The move to notes.parabolic.studio (D99) starts every browser with an empty cache on the new origin, and a browser is bound before an account first opens there, so there is no older cache to migrate.
- A browser without local storage cannot hold a device secret; it keeps expiry behaviour (it also cannot keep the cross-domain session).
- After a device is revoked while signed in (it had copies from before a reset), the person signs in once more after the clear; the first session is left to expire.
- A password reset does not remove passkeys; the person removes any unrecognised passkey in Settings.
- Reset-token timing: scheduling the email is one extra write only when the account exists; Better Auth already simulates the lookup for unknown addresses.
- The scheduled reset job carries the token in its arguments (Convex dashboard access already exposes the verification table, where Better Auth stores reset tokens).
- Re-confirming the password to add a passkey creates a new session on that device; the previous one stays valid until it expires.

## Response to Astra review round 1

| Finding                                                       | Response                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1 — reset could commit without its revocations               | `passwords.finishReset` performs every effect of a successful reset in one Convex mutation (component adapter calls from a mutation share its transaction). A failure rolls everything back and the link stays usable. Fault-injection test in `tests/reset-atomicity.test.ts`. |
| A2 — a delayed passkey ceremony could replace a newer login   | `passkeyCeremony` binds the ceremony to the sign-in state it began in, cancels the browser prompt when that state changes and refuses the verification before a session is stored.                                                                                              |
| A3 — late reset completion could undo a newer logout or login | `signInAfter` signs in automatically only if the session generation, the cross-domain intent and the stored session are unchanged since the request began; the invitation page uses the same guard.                                                                             |

## Response to Astra review round 2

Round 2 confirmed A1–A3 fixed and found B1–B6; all are addressed.

| Finding                                                        | Response                                                                                                                                                                                                                                                                    |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1 — an in-flight old-password login could survive a reset     | Session creation re-checks: the hook reads the reset count, then verifies the password against the current credential, and stamps the count on the session; the session trigger refuses a moved count inside the write transaction.                                         |
| B2 — a stale reset answer could erase a newer session's copies | The no-session answer is discarded (transient) if any sign-in or sign-out happened in any tab since the check began; the answer itself is per device and changes once another tab binds.                                                                                    |
| B3 — re-authentication or missing metadata bypassed cleanup    | Server device records, independent of the current login: a live session for a browser behind the reset count is reported revoked (after binding, so the next sign-in opens). Browsers are bound before an account first opens, and D99 means no cache predates the records. |
| B4 — the resetting device could delete its own work            | `finishReset` binds the resetting browser's secret to the new count in the reset transaction itself, so no check, delayed response or other tab can find it behind.                                                                                                         |
| B5 — successful recovery reported as failure                   | `signInAfter` catches a cut-off sign-in and reports it; the page shows the completed reset or account with a sign-in link. A lost reset response says the change may have happened.                                                                                         |
| B6 — `resetSince` exposed reset history                        | Removed. `devices.status` answers only the holder of a browser's secret, about that browser.                                                                                                                                                                                |
