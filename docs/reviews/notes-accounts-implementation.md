# Notes accounts — sign-in, passkeys, password reset and account email

Date: 2026-10-18. Branch `feat/notes-accounts`. Owner request: "we need a proper login and signup flow", with decisions D95–D99 (invite-only stays, passkeys in v1, email from notes@parabolic.studio, a reset wipes other devices, the app moves to notes.parabolic.studio). Independent review is recorded separately.

Any failure leaves nothing changed and the link usable. The HTTP `/reset-password` path is disabled so the choice cannot be skipped. Settings "Change password" emails the same link. |
| Account email                                   | Better Auth runs in Convex, which cannot hold the Cloudflare `send_email` binding, so Convex posts to the Worker's `/internal/email` with a shared secret (`EMAIL_RELAY_SECRET`, compared in constant time over SHA-256 digests). The relay renders only its own two templates and only for links on its own origin with a token-shaped fragment; recipient, labels and size are validated, names are stripped of control characters and HTML-escaped. Sends are limited to 3 per hour per account (reset) or invitation, and 100 per day overall (`emailSends`, pruned daily). Nothing logs a recipient, link or token.                                                                                                                                                                                                                 |
| Session controller                              | One additive method, `settled()`: resolves once no sign-out is still talking to the server. Sign-out shows the signed-out screen first and clears the stored credential last (by design); a passkey or reset request begun in between was superseded by the cross-domain client's request guard and its challenge cookie lost. Passkey sign-in (button and autofill) and reset requests wait for `settled()`. No lifecycle behaviour changed.                                                                                                                                                                                                                                                                                                                                                                                            |

## Protected areas touched

- **Auth storage**: switching the Better Auth component from the npm default to a local install. The docs do not state whether data survives, so this was rehearsed on the cloud dev deployment: an account and a live session created on the old component were both valid after the push, password sign-in still worked and the passkey endpoints answered. The 42 existing backend tests pass against the local component.
- **Auth configuration** (`convex/auth.ts`): passkey plugin, reset lifecycle (`revokeSessionsOnPasswordReset`, one-hour tokens, scheduled send), `/reset-password` added to `disabledPaths`.
- **Session lifecycle** (`apps/notes/src/session.ts`): the additive `settled()` only.
- **Agent connections**: `connections.disconnectAgents`, called only inside the reset transaction with the person's explicit choice. Notebook memberships are untouched.
- **Device revocation** (D98): `auth-service.ts` may now return `revoked`, only after two server answers (no session; reset since this device signed in).
- **Hostname**: the production origin moves to `notes.parabolic.studio` (D99).
- **Hostname trust**: the relay accepts links only for `PUBLIC_ORIGIN` paths `/reset#` and `/invite#`.

## Known limits and pending work

- **Sender domain.** parabolic.studio was onboarded by the owner on 2026-10-18 (records on `cf-bounce.parabolic.studio`, DKIM, and `_dmarc` with `p=reject`; the apex MX used by Email Routing is unchanged). Delivery is proven only once production sends a real message. Cloudflare Email Sending is in public beta.
- **Revocation needs a session check.** A device learns of a reset only when it next checks its session with the server; a device that stays offline keeps its copies until then (as the spec states).
- **Devices signed in before this release** have no recorded session start until their first successful check after deploy; until then a reset leaves them expired rather than revoked.
- A password reset does not remove passkeys; the person removes any unrecognised passkey in Settings.
- Reset-token timing: scheduling the email is one extra write only when the account exists; Better Auth already simulates the lookup for unknown addresses.
- The scheduled reset job carries the token in its arguments (Convex dashboard access already exposes the verification table, where Better Auth stores reset tokens).
- Re-confirming the password to add a passkey creates a new session on that device; the previous one stays valid until it expires.

## Response to Astra review round 1

The round-1 review (`notes-accounts-round1-astra-review.md`) found three blockers; all are fixed.

| Finding                                                       | Response                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1 — reset could commit without its revocations               | `passwords.finishReset` performs every effect of a successful reset in one Convex mutation (component adapter calls from a mutation share its transaction). A failure rolls everything back and the link stays usable; a failed session deletion is no longer reported as an expired link. Fault-injection test in `tests/reset-atomicity.test.ts`. |
| A2 — a delayed passkey ceremony could replace a newer login   | `passkeyCeremony` binds the ceremony to the sign-in state it began in, cancels the browser prompt when that state changes and refuses the verification before a session is stored. Tests in `apps/notes/tests/unit/sign-in-flow.test.ts`, mutation-checked.                                                                                         |
| A3 — late reset completion could undo a newer logout or login | `signInAfter` signs in automatically only if the session generation, the cross-domain intent and the stored session are unchanged since the request began; otherwise the page reports success and links to sign-in. The invitation page uses the same guard.                                                                                        |

Owner decisions since round 1: D98 (a reset wipes other devices) and D99 (the app moves to notes.parabolic.studio), both implemented above.
