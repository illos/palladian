# Note history (A4) — round 4 independent review

Reviewer: GPT-6-Astra (Codex, high reasoning), delegated read-only on 2026-10-23. Reviewed `0042ef8..df0db7e` on `feat/notes-history`.

---

1. **R4-1 — blocking: failed persistence still permits Restore.** [restore-keeper.ts:107] sends after `change()`, which suppresses storage failures at line 161. A local probe confirmed that a quota failure still dispatches the request; reload loses the hold. Starting another restore can even erase the first in-memory hold. **Fix:** require successful durable recording before dispatch; refuse Restore when storage is unavailable. Test failed writes followed by reload and another restore.

2. **R4-2 — blocking: two windows can erase each other's pending records.** [restore-keeper.ts:157] performs an unlocked read–modify–write of the entire array. A deterministic interleaving probe lost window B's record while its request remained in flight; `reload()` then removed B's hold. The existing two-window test performs sequential writes. **Fix:** use transactional persistence or a cross-window lock for insertion and removal. Test overlapping inserts and insert-versus-completion.

3. **R4-3 — blocking: dispatch is not bound to the recorded account.** [App.tsx:256] captures the shared client, awaits a lazy import, then sends without rechecking identity. [restore-send.ts:18] never checks `record.accountId`. A probe using the exact App callback and actual sender dispatched A's request as B after switching identity during that await. If B can edit the shared note, server authorization permits it; receipts are also actor-scoped. **Fix:** fence dispatch and completion by account/session generation, and prevent queued requests from crossing client authentication lifecycles.

4. **R4-4 — blocking: another window's success unlocks an editor before it receives the restore.** [restore-keeper.ts:130] deletes the shared record immediately; [App.tsx:1339] bases the editing hold on that record. The sender discards the returned revision. A local test using the actual `NoteChannel` showed: another window resolves Restore → hold disappears while this channel still reports Saved → new typing starts → delayed replacement drops that typing. **Fix:** preserve the successful restore's revision and keep each editor locked until its own channel has incorporated it. Test independently delayed step delivery and mutation responses across windows.

5. **R4-5 — should fix: pending records lack an account-cleanup and retention contract.** Sign-out only clears `NotesStore` ([main.tsx:67]); pending restores remain and automatically replay on a later sign-in. Records have no count/size bound, and weak validation silently discards malformed entries ([restore-keeper.ts:54]). D28 explicitly covers cached notes and attachments, so an IDs-only safety record is not automatically a demonstrated violation, but its retention needs an explicit contract. **Fix:** integrate restore settlement/cancellation with account cleanup, or document an approved minimal safety-record exception. Bound storage by refusing additional operations rather than evicting unresolved holds; provide corruption recovery. Simply deleting pending records at sign-out would recreate the safety gap.

6. **R4-6 — should fix: replay failures can misreport an already-applied restore.** [history.ts:120] checks current access before consulting receipts. If Restore applied, its answer was lost, and access was subsequently revoked, replay returns a refusal, not the original outcome. [versions.ts:119] nevertheless says "The restore did not apply." **Fix:** distinguish current refusal from confirmed historical non-application. Ordinary `denied`/`not_found` responses do clear the record, so lost access alone does not leave a permanent hold.

Server replay otherwise passed two local `convex-test` probes: old receipts return the original revision, and conflicts remain conflicts after further edits. No receipt expiry exists. R3-2, R3-3 and R3-4 look correct.
