# P1 automatic-resume investigation

Date: 2026-09-10. Read-only runtime investigation; this is not phase acceptance.

## Findings

The existing A03 test does not establish browser suspension. In the pinned Playwright 1.63.0 / Chromium 153 environment, `chromium.launch()` enables focus emulation on Playwright's own DevTools session. Calling `Page.setWebLifecycleState({state: "frozen"})` through a separate session while the page remains visible returns successfully, but a timer scheduled for one second still executes one second later, during the supposed 2.5-second freeze. No `freeze`, `resume`, or visibility event is delivered. The same result occurred with lifecycle reporting enabled, headed Chromium under an ephemeral Xvfb, and a second foreground page. These probes used a blank page; one unsigned-in timing-only probe visited localhost:5173. No credentials or session fixture was used.

Pinned source evidence: Playwright `lib/coreBundle.js` calls `Emulation.setFocusEmulationEnabled({enabled:true})` during main-frame initialization. The supported `connectOverCDP` option `noDefaults:true` skips those overrides for the default context. Chromium's scheduler accepts hidden-to-frozen transitions, as described in its [page scheduler source](https://chromium.googlesource.com/chromium/src/+/HEAD/third_party/blink/renderer/platform/scheduler/main_thread/page_scheduler_impl.cc) and the [Chrome lifecycle documentation](https://developer.chrome.com/docs/web-platform/page-lifecycle-api).

A bounded actual-browser control succeeded by launching the pinned Chromium executable directly, attaching Playwright with `connectOverCDP(..., {noDefaults:true})`, using the default context, and opening a foreground blank page before freezing the tested page. The redacted timing trace was: hidden at 5 ms; freeze at 69 ms; resume at 2570 ms; visible at 2574 ms; the one-second timer executed at 2574 ms. This is a genuine desktop JS-suspension probe; it is not iPhone evidence.

The old test also resets its token observer before the long waiting interval, so a renewal during a no-op freeze could satisfy its final assertion. A corrected test must require actual suspension and record fresh issuance after thaw. The previous report remains evidence that its observation assertion failed, but cannot establish a genuine suspended-tab resume defect.

There is an independent scheduling concern in the pinned official Convex client. `authentication_manager.ts` first fetches a token, receives server confirmation, and normally immediately demands another. If that returns the same JWT, `refetchToken()` transitions to `notRefetching` without scheduling the next proactive refresh. The browser then depends on a server auth error to reacquire a token. A bounded actual-service browser diagnostic against the verified Palladian development frontend at localhost:5183 and local anonymous Convex at 3214/3215 observed exactly two startup token responses whose JWTs were identical, with protected account readiness succeeding. This establishes the branch's relevance. It does not prove that branch caused the previous incorrectly frozen A03 observation.

`initialAuthTokenReuse:true` is a typed, official but explicitly experimental Convex option in installed 1.45.0. After the initial token has been confirmed by the server, it schedules renewal from the token's remaining lifetime using the server clock-skew estimate, avoiding the redundant immediate issuance. This preserves the 900-second JWT policy and official token acquisition. The independent P1 reviewer approved this bounded configuration after the equality evidence; the parent implementer enabled it. A new disposable-owner browser diagnostic observed one startup token response and successful protected readiness. This proves the immediate duplicate issuance disappeared; the full real-expiry regression remains required. Future Convex upgrades must recheck this experimental option's supported semantics and the full lifecycle suite.

## Proposed proof

1. Correct the browser harness and demonstrate hidden/freeze/resume events plus delayed timer execution in a short browser-only preflight before spending 15 minutes on expiry.
2. Run production-built Palladian on its verified trusted local origin with a disposable owner against the actual local anonymous Convex deployment. The unrelated service currently at localhost:5173 must not receive authentication fixtures.
3. Record only allowlisted timing, token-response counts, token equality, and expiry booleans. Do not record token bodies, cookies, private responses, or raw websocket frames.
4. Establish protected access and the initial token, freeze a genuinely hidden document, and wait beyond the token's actual expiry plus the verifier's five-second tolerance. Require real-server denial of the old token.
5. Clear the post-resume response observer immediately before thaw, require freeze/resume and suspended timer evidence, and observe automatic issuance of a different unexpired token within the existing 30-second limit, no navigation, stable protected identity, and restored browser private UI. No direct browser token demand, fake clock, reduced JWT lifetime, refresh timer, or relaxed assertion.
6. Independently review any `initialAuthTokenReuse` choice; test its initial same-token/scheduling semantics using installed official code and rerun the real-service acceptance suite, including failed acquisition and logout/account-switch races. Mock manager tests establish code-path behavior only.

## Implemented harness correction and review

`tests/auth/lifecycle-browser.mjs` launches the installed browser with an ephemeral local profile, uses a loopback ephemeral DevTools port, and closes its own process/profile afterward. `node tests/auth/lifecycle-preflight.mjs` requires real hidden/freeze/resume behavior and a one-second timer suspended for at least 2.5 seconds. The implementer observed 2522 ms and 2524 ms passes. The independent reviewer separately observed a 2522 ms lifecycle pass and found a temporary-profile cleanup race; the helper was corrected to await child closure, handle spawn failure/signal exit, close the actual browser, and retry transient profile deletion. The reviewer reran the corrected helper successfully (2522 ms, exit 0) and approved the bounded harness/configuration correction for the full integration test, with no remaining blocker found in that diff.

`tests/auth/resume.mjs` now imports the verified frontend-origin guard, proves freeze before expiry and suspension through expiry plus six seconds, and requires the one-second timer to run after resume. Its post-resume observer accepts only requests dispatched after thaw begins, checked again after asynchronous response-body parsing; a delayed pre-thaw response cannot qualify. Old-token denial accepts the protected query's HTTP 200/null response or HTTP 401 authentication rejection, not network errors, rate limits, or 5xx responses. The 30-second automatic-renewal, no-navigation, distinct unexpired JWT, stable identity, and browser private-account assertions remain.

The diagnostic owner fixtures used actual Better Auth and Convex; only response counts/equality booleans were printed. No credential, JWT body, raw websocket payload, or private content was logged. These bounded diagnostics ran against development assets and are not production-build resume proof. No real-time JWT expiry test, production deployment, iPhone, installed PWA, or hosted-origin test was performed in this investigation; these remain pending.
