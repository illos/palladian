# Notebook management (port plan A5)

Date: 2026-10-22. Branch `feat/notes-notebooks`, based on `feat/notes-pins-sorts` (`3af8da4`: A6 with its review round 1, on A2's round 1 `ce30705`; both in review), because deletion must clean up A6's per-person orders and positions and the menus reuse A2's `ActionMenu`. Owner request to work through the Deltos UI in the agreed scope ([plan 08](../specs/notes-app/08-deltos-feature-port.md), A5).

**Protected areas touched, for independent review:**

- **Authorization:** a new owner-only mutation, `notebooks.remove`, deletes a notebook and files its notes elsewhere; a new query, `notebooks.deletePreview`, says who would lose access. Existing rules are unchanged.
- **Lifecycle and sharing paths:** the bodies of `lifecycle.move`, `notes.trash`/`restore` and `sharing.setNoteRestricted` moved, unchanged, into helpers (`moveNote`, `changeLifecycle`, `changeRestriction`) that deletion also calls. (Round 1 restored `lifecycle.movePreview`'s own loop, which the deletion preview no longer shares.)
- **Note creation (round 1, a narrow contract change):** `notes.create` and `notes.createFromMarkdown` file a person's note in their default notebook only when the notebook it names was deleted by that same person. Every other case, and every agent, is refused exactly as before. See [Creation into a deleted notebook](#creation-into-a-deleted-notebook-limited-by-d86).
- **Arrangement:** a new scheduled cleanup, `arrangement.forgetNotebook`, next to A6's `forgetStale`.
- **Schema:** three indexes (`invitations.by_notebook_and_accepted_at_and_revoked_at`, `listOrders.by_list`, `notePositions.by_notebook`) and, in round 1, one small table, `deletedNotebooks` (`notebookId`, `ownerId`, `deletedAt`, indexed by notebook), written by the call that deletes the notebook row and kept for good.

`cache.ts`, `live.ts`, `channel.ts`, `binding.ts`, `session.ts`, `logout.ts`, `main.tsx` and `editor.tsx` are unchanged, as are `selectNote`, `makeChannel`, `accessLost` and `openRemote` in `App.tsx`. Nothing was pushed to a Convex deployment; `_generated` was regenerated with `convex codegen` (no file changed).

## Deletion: design and rules

`notebooks.remove({ notebookId, destinationId, trash })` returns `{ done, notes }`. The app calls it until `done`.

| Question                               | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Who may delete                         | Only the notebook's owner, signed in as a person (`requireHuman`, then `ownerId` equals the caller). Members with edit or read access are refused ("Only the notebook's owner can delete it"). Agents are refused even with every owner delegation ("Only people can perform this action"). Signed-out callers are refused.                                                                                                                                                                                                                                                                                                                                                                                                         |
| A notebook the caller cannot see       | Reported as `{ done: true, notes: 0 }` with no change, exactly as for a notebook that is already gone. Repeating a finished deletion is therefore harmless, and the call tells a stranger nothing about whether an ID exists.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| The default notebook                   | Refused ("Choose another default before deleting it"), checked on every call, so setting it as default part way stops the deletion.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Where the notes go                     | Always to a destination: another notebook the caller owns, checked on every call. With `trash: false` they stay there as they are; with `trash: true` they go to Trash there.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Why Trash needs a destination          | Trash keeps a note's notebook (D59; spec 02). Notes left behind in a deleted notebook would reach no library feed of their owner's (feeds are per notebook) while staying visible to anyone with a per-note grant. Filing them first gives each one a home, which is where Restore puts it.                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| How each note moves                    | Through the move path, `moveNote` (taken unchanged from `lifecycle.move`): a feed tombstone in the old notebook, the destination's next sequence, the search projection, and `arrangement.forgetStale` scheduled for its old positions. ID, history, pins and public link stay with the note.                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| How notes reach Trash                  | Through the trash path, `changeLifecycle` (from `notes.trash`): lifecycle, `trashedAt`, the search flag and the feed entry. A note already in Trash keeps its `trashedAt`, so its retention still counts from when it went there.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Notes that end up in Trash             | When the destination has any member (person or agent), each note sent to Trash, and each note that was already there, is made private (`restricted`) through the sharing path, `changeRestriction`. So nobody gains access to trashed notes through the deletion. It stays private after Restore; the owner can open it up again in Share. A destination without members leaves the setting as it was.                                                                                                                                                                                                                                                                                                                              |
| Restricted notes                       | Stay restricted (the move path keeps the flag).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Per-note grants and "No access"        | Kept, as with any move (D50). A grantee keeps access, including to a note now in Trash, as for any trashed note; an explicit "No access" still overrides the destination's membership.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Notes owned by someone else            | Cannot arise through the app: notes belong to their notebook's owner (D15) and move only between one owner's notebooks (D51). If one is found, the call fails with "This notebook holds a note owned by someone else" and its whole batch rolls back, so the notebook stays, intact.                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| After the notes                        | Memberships are deleted. Open invitations to the notebook are revoked, as Revoke does (`revokedAt`), so their links say "revoked". Accepted invitations stay as the record of grants already made (their memberships are deleted above; `sharing.candidates` still suggests those people). Then the feed's tombstones, the sequence counter and the notebook row are deleted.                                                                                                                                                                                                                                                                                                                                                       |
| Orders and positions                   | Everyone's `listOrders` for the notebook and `notePositions` in it are removed by `arrangement.forgetNotebook`, scheduled in the final call, 200 rows per run, rescheduling itself until none remain (as A6's `forgetStale`). `arrangement.mine` already hides them: the list is no longer reachable.                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Pins                                   | Unchanged. Pins are personal and per note; they follow moved notes. People who lost access have theirs hidden by `arrangement.mine` and reclaimed at the pin quota (A6).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Transaction limits                     | One phase per call: notes, or else up to 400 cleanup rows. A call files up to 50 notes and stops before the search text it reads would pass 8 MiB (round 1): measuring a note reads its search text once, the move reads and rewrites it, and Trash does so again, so a note counts two or three times its UTF-8 size, plus 8 KiB. Writes are at most two-thirds of that. Every call files at least one note: no Convex document exceeds 1 MiB, so the largest note costs about 3 MiB read and 2 MiB written, within the 16 MiB limits. `done` is false until the call that deletes the notebook row, which runs only when it finds no notes left, in the same transaction.                                                         |
| Members adding notes during a deletion | Possible until the memberships go, after the notes. Each call takes the notes that are there, so late notes are moved too; the notebook is deleted only by a call that finds none.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Repeating, or changing the choice      | Each call applies its own arguments to what is left. A call after `done` returns `done` again.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| The preview                            | `notebooks.deletePreview` (owner only, else null; rewritten in round 1) names each member who would lose a note they can open now. A member loses a note they open through the notebook (not restricted, no explicit grant of theirs) when they are not in the destination, or when the note ends up private in Trash there, which covers notes already in Trash. Explicit grants, "No access" included, keep deciding; restricted notes are opened only through them, so they take nothing. It examines up to 200 members and 500 notes (and 5,000 grants); beyond that, `complete` is false and the dialog says the list may not name everyone. It answers with its destination and choice, so the dialog can tell it is current. |

Differences from plan 08 A5, deliberately:

- **Trash needs a home.** The plan offers "move the N notes to another notebook or to Trash". Trash keeps a note's notebook, so the Trash choice also names a notebook, where Restore puts the notes.
- **Trashed notes become private in a shared destination.** Not in the plan; it is the conservative rule for the case above.
- **Invitations are revoked, not deleted.** Open invitations stop working and say "revoked"; accepted ones stay as records.
- **Orders and positions are cleaned up after the deletion** in scheduled batches, as A6 does for moves (coordinator direction after A6's review round 1); reads hide them meanwhile.
- **Delete is offered on the default notebook**, whose dialog asks for another default first, rather than being hidden without explanation.
- **The list header's "…" shows on all widths**, not only phones: it is the keyboard and screen-reader route on desktop.
- **Sort is not in the notebook menu.** A6 put a Sort select in the list header, which covers it.
- **Counts are a visual aid**, hidden from assistive tech (see Counts).

## Creation into a deleted notebook, limited by D86

D86 governs this. `04-documents.md`: "Confirmed: users cannot export unsaved work after notebook access is removed. Proposed: after effective note access is lost, purge its pending local content and deny recovery into a separate note." So the fallback rescues only the owner's own work.

- **Only the person who deleted the notebook.** The call that deletes the notebook row writes a `deletedNotebooks` record (`notebookId`, `ownerId`, `deletedAt`). When a **person** creates a note naming a notebook, and that record exists with them as `ownerId`, the note goes to their default notebook (with no usable default, the existing rules for a note without a notebook apply). This covers the owner's other devices, live or offline, that had not yet learned of the deletion: F1's typing loss and F3's stranded draft, for the owner. `createFromMarkdown` follows the same rule for people; the app does not call it, and MCP callers are agents.
- **Everyone and everything else, exactly as before**, with the same error code and message: a collaborator creating into a notebook its owner deleted, and anyone who never had access ("Notebook not found."); a removed member ("Notebook not found."); a read-only member ("This action needs edit access to the notebook."); and every agent call, the owner's own agents included. A collaborator's draft therefore follows the existing access-loss path and is purged, as D86 requires. The three refusal tests pass on `b017c45` too, which shows the behaviour is unchanged.
- **Checked first, as before:** the `clientKey` replay check (a replay of a note the person can no longer open is "not found") and the `sourceNoteId` conflict-copy check (a copy of a note the person cannot open is refused, whatever notebook it names).

On the client, the navigation changes stay: a notebook that leaves the cached list stops being shown, and New note targets only listed notebooks that take the person's notes. They narrow the window in which a collaborator could type into a notebook that has gone.

Recovery placement for the owner's own drafts is part of open question Q11; this places them in the owner's default notebook.

## Found during this work (not changed)

- **Other devices may briefly hold moved notes.** If a device learns that the notebook is gone before the destination's feed delivers the moved notes, the existing access reconciliation holds those notes (keeping drafts) until the feed delivers them and `verifyAccess` lifts the hold. They disappear and come back. No data is lost; this is the existing fence behaviour.
- **All Notes' count includes Trash**, while notebook counts leave it out (as the plan asks). All Notes lists trashed notes too (spec 02), so its count matches its list.
- **The Move dialog's preview examines at most 200 members**, silently (`lifecycle.movePreview`, unchanged since before A5). The deletion preview now discloses its bounds; the Move dialog does not.
- **A draft's notebook follows the list shown while it is typed.** `persistDraft` stores the notebook of the current list on every write, so switching lists while typing an offline draft changes where it will be created. Now limited to listed notebooks that take the person's notes; the behaviour itself predates A5.
- **Phone list headers hide their link buttons.** Below 760 px, `.library-header button { display: none }` hides "Sharing"/"Members" and "Empty Trash". The notebook "…" is exempt; the others were left as they are.
