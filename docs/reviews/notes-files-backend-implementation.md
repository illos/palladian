## Design

### Document schema (B2, `packages/notes-core`)

| Element      | Attributes                                                                                                                                            | Markdown                                                         |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `image`      | existing `src`, `alt`, `title`, plus `width` (integer CSS pixels, 32–4096, or null for natural size)                                                  | `![alt](attachment:<objectId>){width=480}`                       |
| `file` (new) | `objectId`, `name` (1–255 characters, no control characters, no outer spaces), `mimeType` (lowercase `type/subtype` or empty), `size` (bytes or null) | `[name](attachment:<objectId>){type=application/pdf size=24576}` |

- **References.** `attachment:<objectId>`, where an object ID is 16–64 characters of `[a-z0-9]` (real Convex IDs and convex-test IDs both fit). New content may use `https:` or exactly that form (`isSafeImageSource`); anything else (paths, queries, upper case, other schemes) is rejected. Stored documents may keep older sources (see Compatibility).
- **Validation everywhere documents are validated.** Submitted documents (`parseSubmittedDoc`, for new notes), stored JSON (`parseStoredDoc`), every step (`applySafeStep`: inserted content and attribute changes), DOM parsing (`parseDOM` refuses invalid attributes), and Markdown (invalid attachment links stay text; invalid attribute blocks stay literal text).
- **Markdown attributes.** Pandoc-style braces, directly after the image or link. Only known keys with valid values are read, otherwise the braces stay text. File names and image descriptions are escaped, including `<` and `>` (an autolink would form) and `&` before an entity, so every valid name round-trips; an attachment link's closing token is matched structurally, so a link inside an agent's label cannot break parsing (review F6). An attachment link anywhere in a paragraph is lifted out as a file block, as images already were. Inside headings, images and files become their text; previously, an image in a heading made parsing throw.
- **`attachmentIds(doc)`** is the single definition of "this document references these objects", used by the backend. File names count as plain text for search and previews.
- **Compatibility.** Images stored without `width` read as null. The Deltos placeholders ("📎 name (file to be added)") are plain paragraphs and are unaffected. Upload placeholders are not nodes (B3 decorations), as planned.
- **Legacy image sources (review F7).** Before B2, an image could have any `attachment:` source (any case, outer spaces). Stored documents, meaning current content, checkpoints, history and cached copies, may keep such a source: they still open, edit (including resizing that image) and replay. The source names no object, so it grants nothing and shows as unavailable. New content cannot introduce one: new notes, inserted content, a changed `src` and Markdown are checked strictly. `files.scanAttachmentSources` and `scripts/scan-attachment-sources.ts` find them (see Deploying).

### Data model (B1, `apps/notes-backend/convex/schema.ts`)

- **`objects`**: owner, uploader, the note or notebook it was uploaded for, name, media type, size, SHA-256, state (`pending`, `ready`, `failed`), hashes of the upload tickets, `expiresAt`, `leaseUntil` (until when an admitted upload may write), an optional `requestId` with a request digest, `createdAt`, `readyAt` and `trashedAt`. The R2 key is `objects/<_id>`, never a content hash, so objects in shared notebooks cannot collide, and an object deleted and re-uploaded is a different object.
- **`objectRefs`**: one row per (note, object) the note has ever referenced. `current` means the accepted document references the object now. `live` means current and in an active note.
- **`objectDeletions`**: tombstones for R2 keys whose bytes must go. When one is due (`notBefore`), the sweep re-reads its object in the same transaction. It hands the key to the Worker only if the object is then gone or failed; a pending or ready object's tombstone retires without a deletion (R3-1). After each confirmed pass the tombstone records it (`passes`, `lastPassAt`) and is due again the next day, until `retainUntil`: seven days after the object's upload lease ended, or one pass if it never had a lease (R2-2).
- **`objectRefs` proofs**: each reference row records how its access was proven when it was first recorded: `proof` is `uploader`, `source` or `search`, with `proofNoteId` naming the note (review R2-1, R2-3).
- **Owner.** An object belongs to the owner of the note or notebook it was uploaded for, whoever uploaded it; notes already work this way. That owner's Trash retention governs it (D34).

### Upload protocol

1. **Ticket.** The app or an agent calls `files.createUpload({ noteId | notebookId, name, mimeType, size, sha256, requestId? })`.
   - It needs edit access to the note (an active one), or to the notebook for a new file note.
   - It cleans the name and normalizes the media type (parameters dropped, unknown types become `application/octet-stream`).
   - It creates a `pending` object and returns its ID with a 32-byte random ticket, valid for one hour. Only the ticket's SHA-256 is stored.
   - A retried `requestId` with the same content returns the same object: a fresh ticket while it is pending (older tickets keep working), or its state once ready. Different content under the same `requestId` is a conflict.
2. **Bytes.** `PUT /files/upload/<objectId>` with `Authorization: Bearer <ticket>`. The ticket never goes in a URL.
   - The Worker asks `files.admitUpload` for the expected size, SHA-256 and type. Admission grants a 15-minute write lease (review F3).
   - It reads at most that many bytes, refusing early when `Content-Length` disagrees or exceeds 25 MB, and checks size and SHA-256.
   - It writes R2 only before the lease ends (408 `too_slow` otherwise), passing the SHA-256 so R2 verifies it again, and calls `files.finalize`.
3. **Idempotency.** The object ID is fixed when the ticket is issued, so no retry can make a second object.
   - An object that is already ready answers 200 without reading or writing.
   - A repeated pending upload writes the same key with the same verified bytes.
   - `finalize` on a ready object answers ready.
   - If finalizing has an unknown outcome (503), the bytes stay; a retry settles it.
   - If Convex says the object will never be ready (expired, failed or deleted), the bytes stay for the object's tombstone: the Worker never deletes (R3-1).
4. **Expiry.** Tickets expire after an hour. An upload accepted before expiry may still finalize for 15 minutes more. An hourly sweep marks older pending objects `failed` and queues their keys for deletion; failed records are removed a day later.
5. **Late writes after deletion (review F3, R2-2, R3-1).** The Worker writes only before its lease and never deletes bytes. Each object has its own key, and the Worker checks size and SHA-256 before writing (R2 verifies the checksum again). So any write to a key, however late, carries exactly that object's bytes: a late write for a ready object rewrites the same correct bytes. Bytes go only when Convex decides, through tombstones. Every deletion of an upload is re-done daily until seven days after its lease, and each pass deletes only if the object is, at that moment, gone or failed. Residual risk: a write that completes more than seven days after its lease would stay as unreachable bytes.
6. **Mismatched bytes** answer 422 and leave the ticket usable until it expires, so an interrupted upload can be retried.

### Worker ↔ Convex for the file service

The Worker already talks to Convex with short-lived ES256 JWTs it signs with `AGENT_JWT_PRIVATE_KEY` (issuer `AGENT_JWT_ISSUER`, audience `palladian-convex`). The file service uses the same key and issuer with subject `service:files`, no `cid` claim, and a 60-second lifetime (`mintServiceJwt`).

- `files.admitUpload`, `files.finalize`, `files.deletionBatch` and `files.confirmDeletions` accept only that subject from that issuer. All four are mutations: `deletionBatch` depends on the time, and a cached query result would keep answering for an earlier time.
- The Worker mints a fresh token for every call, so a slow upload or a long deletion sweep never runs on an expired one (review F5).
- `getPrincipal` resolves no person or agent from it, because there is no connection ID. Every existing function therefore treats it as signed out; a test proves it.
- No new secret, Convex environment variable or auth configuration change.

### Reads and how the browser authenticates

- **`GET /files/notes/<noteId>/<objectId>`** with `Authorization: Bearer <Convex token>`. This is the same 15-minute Better Auth Convex JWT that `live.ts` gets from `auth.convex.token()`.
  - The Worker calls `files.authorizeRead` with the caller's own token, so Convex decides with the caller's identity and checks the session is live.
  - Access is granted when the caller can read the note and its current document references the object, or the caller can edit the note (and so view its history) and an earlier revision referenced it.
  - An expired or rejected token gets 401; the client should refresh once and retry (Deltos GOTCHA-0006). No access gets 404, never revealing whether the object exists.
  - No bearer secret ever appears in a URL; the note and object IDs in the path grant nothing on their own. Routes never log URLs, tickets, tokens or names.
- **`GET /files/public/<publicToken>/<objectId>`** needs no account. `files.authorizePublicRead` serves only objects the published note's current content references, only while the link is current and the note is not in Trash (D38). The public link token is already the public capability for that page.
- **Headers.**
  - Only `image/png`, `image/jpeg`, `image/gif` and `image/webp` are served inline with their type. Everything else is `application/octet-stream` with `Content-Disposition: attachment` (RFC 8187 filename).
  - Every response carries `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy: no-referrer`, `Cache-Control: private, no-store` and an `ETag` of the SHA-256.
  - `no-store` keeps bytes out of the browser's HTTP cache, so the app-managed cache that sign-out clears is the only copy (D28). GET and HEAD are supported; Range requests are not.
- **B3 client contract.**
  - Fetch with the header, make a `blob:` URL, and cache bytes per account by object ID; an object ID never changes content.
  - `files.noteObjects({ noteId })` lists a note's current objects with state and Trash flag.
  - In local development the SPA (Vite, port 5178) and the Worker run on different origins and the Worker sends no CORS headers, so B3 needs a dev proxy for `/files`.

### References and the object lifecycle (D36–D42)

Every accepted revision records its references in the same transaction. `commitSteps` (app pushes, agent edits, history restore) and `createNoteRecord` (new notes, copies, duplicates, imports) both call `recordReferences`. In `commitSteps`, each step is a revision. Objects any step brings in (`stepAttachmentIds`: replaced content, or an attribute step pointing an image or file elsewhere) are recorded too: as current references if the final document has them, otherwise as history references (review F2). The `commitSteps` change keeps the previous document, collects those IDs while applying steps, and calls `recordReferences` before anything is written. It can refuse an edit only when one of its revisions would exceed 200 attachments (each accepted revision must stay restorable, R2-5; the count is exact for any step that brings one in once the batch's union passes 200), or one change would add more than 200 (`too_large`, the same family as the existing size limit).

A new reference is recorded only when the actor may already use the object:

- they uploaded it;
- this note referenced it before (undo, history restore);
- they can read a note whose current document references it, or edit a note that referenced it earlier (copy and paste, Duplicate, conflict copies).

How that is decided, once, inside the accepting transaction, within Convex's limits (review F1, F4; changed in round 2, R2-1 and R2-3):

- **Named source notes.** `notes.create` (`sourceNoteId`, already there for conflict copies), and `notes.push`, `notes.edit` and `notes.createFromMarkdown` (`sourceNoteIds`, at most 3, optional) name where new attachments came from. A source proves access by the same rule as reads (R3-2): the actor can read it now and its current content references the object, or the actor can edit it and an earlier revision referenced it. This is one exact lookup per source, independent of the search budget. The MCP `create_note` and `edit_note` tools pass `source_note_ids` through, and the server instructions tell agents to use it when copying an attachment line. B3 passes the source of a paste.
- **Bounded search.** Otherwise the references of the object are searched as `authorizeRead` would allow them (current references with read access, earlier ones with edit access), with roles looked up once per note. One change may examine 48 reference rows in total. Each object gets a fair share of what is left, at least 8 rows, so a single copied object can use all 48.
- **Unproven means never.** If none of these proves access, the reference stays in the document but grants nothing and keeps nothing alive, now and later. Access gained afterwards does not upgrade it; only removing it and adding it again with a proof does. There is no deferred verification: round 1's `files.verifyReference` and `referenceChecks` are gone (they could complete after a connection or destination grant was revoked, R2-1). A proven reference stands on its own: revoking or deleting its source later changes nothing, and it keeps the object alive like any reference (R2-3). A copy of an object with many references must therefore name its source to be sure of proof.
- **Budget.** At most 200 new and 200 removed objects per change. Per new object: about eight reads (the object, this note's row, one per source, two search ranges while the budget lasts, its live references). Per removed object: three. Note roles: at most 51 notes, three reads each, memoized. In the worst case that is about 2,400 index ranges and gets together, under the 4,096 Convex allows. Every file test runs with convex-test's limits enforced, and the worst cases run under a 2,000-range cap so that the gets convex-test does not count still fit.

Otherwise the document keeps the reference (the edit is not refused, so a collaborative client is never wedged), but it grants nothing and does not keep the object alive. It reads like a permanently deleted object. Without this rule, anyone who learned an object ID could put it in their own note and read the bytes.

| Event                                                                  | Effect                                                                                                                                                                                                                                                                                                                     |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ticket issued                                                          | `pending`; not readable                                                                                                                                                                                                                                                                                                    |
| Finalized                                                              | `ready`. If no active note references it yet, it counts as unused from now (`trashedAt` set)                                                                                                                                                                                                                               |
| An active note's accepted document gains it                            | Live reference; the object leaves Trash (`trashedAt` cleared)                                                                                                                                                                                                                                                              |
| The last live reference goes (edit removes it, or the note is trashed) | Object enters Trash; `trashedAt` = now, never reset if already set (D41, D42)                                                                                                                                                                                                                                              |
| Note restored, or a history revision restored                          | References become live again; still-trashed objects revive (D37)                                                                                                                                                                                                                                                           |
| Owner's retention passes (daily, 04:53 UTC)                            | Permanently deleted if no existing note's current content references it (Q11 below); manual-only retention keeps it                                                                                                                                                                                                        |
| Never referenced by any note for 7 days                                | Permanently deleted (an abandoned upload), whatever the retention                                                                                                                                                                                                                                                          |
| Note permanently deleted (manual or retention)                         | Its reference rows are removed in scheduled batches; objects no other note ever referenced are permanently deleted with it (D90); others keep their own Trash clock                                                                                                                                                        |
| Upload cancelled (`files.cancelUpload`)                                | Pending becomes `failed`; a ready object no note ever used is deleted. Either way its key gets a tombstone: deleted at the next sweep and again daily until seven days after its lease                                                                                                                                     |
| Permanent deletion                                                     | The `objects` row goes now and reference rows in batches. The R2 key gets a tombstone, deleted by the Worker's next daily sweep and again until seven days after any upload lease. A document reference to it reads as "attachment permanently deleted": it is absent from `noteObjects`, and the Worker answers 404 (D40) |

Note trash, restore and permanent deletion update references through a scheduled, batched `files.syncNote`. This follows the pattern A6's review introduced for pins and positions. `syncNote` reads the note's state when it runs, so running late, twice or out of order is safe. Convex serializes the transactions, so a reference change, a lifecycle change and a purge cannot interleave inconsistently. A late reference to a purged object is accepted but not recorded.

### Q11 choices (conservative, for the owner to confirm)

- **Cross-owner references.** A person who can read an object may reference it in a note with another owner (copy and paste, Duplicate into their own notebook). The object keeps its owner and that owner's retention. It stays active while any active note uses it, whichever owner's.
- **Notes in Trash.** An object a note in Trash still contains is never purged, even after the object owner's retention has passed. Restoring that note within its own retention gets the attachment back.
- **History.** Historical references do not keep bytes (D37). They only let editors view the object while it exists.
- **Revoked access.** Someone who copied an attachment into their own note keeps it after losing access to the original note. That is equivalent to having downloaded it.
- **Never deleted** are bytes that any existing note's current content still references.

### Agents (MCP `attach_file`)

Spec 05 defines the "Attach file" family as an upload, finalize and reference workflow with no whole-body rewrite and explicit size and type limits. It does not say how bytes reach the server. I implemented the narrowest form, matching Deltos's `embed_file`: bytes as base64 in the call, at most 2 MB.

1. The tool gets a ticket as the agent, so the agent's own edit access applies.
2. The Worker stores and finalizes the bytes as the file service.
3. One targeted `notes.edit` (`append`, or `insert_after` a block) adds `![name](attachment:id)` for the four inline image types, or a file block otherwise.

The `request_id` makes the whole call retry-safe; a replay attaches nothing twice. No URL fetching (that would make the Worker fetch arbitrary addresses), no download tool, no scope change. Read Markdown shows attachments with their names, and the server instructions explain the syntax.

### Files gate and rollout (reviews R3-3 to R5)

Clients built before B2, every build up to `main` `0042ef8` (A3 included), cannot open a note containing a `file` block. Their schema has no such node: `Unknown node type: file`. Images with a `width` or an `attachment:` source do open on those clients but show nothing useful: the width is ignored and the image is broken. The app's offline plugin keeps an old build running until all its windows close, so deploying a new app does not upgrade every device at once.

So new content cannot use files until the owner turns them on. `FILES_WRITES_ENABLED` is a Convex environment variable, off unless set to `true`. While it is off:

- `files.createUpload` and `files.admitUpload` refuse with "Files and image sizes are not enabled on this server yet.". MCP `attach_file` reports that message, and the Worker answers `PUT /files/upload` with 403 `disabled`.
- An edit may not bring in a file feature the note does not already have (round 4, R4-2), compared by kind (round 5, R5-1): a file block for an object the note has no file block for, an `attachment:` image of an object the note shows no image of, or an image width the note does not use for that image source. An attachment image, including one stored before B2, never allows a file block for its object, or the reverse: an old client opens the one and not the other. The measure is the note's current document when the edit arrives. This covers every step of a push, agent edit or history restore (`commitSteps`).
- A new note (`createNoteRecord`) may only have the file features, by the same kinds, of the source notes it names and the creator may read. Duplicate (which now names its source) and conflict copies keep their attachments; other new notes have none.
- Reads, `authorizeRead`, existing content, text edits, `replace_all` that keeps identical attachments, `replace_text`, moving or removing attachments, and legacy sources are unaffected.

The refusals use the code `invalid`, as for other content the server will not accept; `denied` would make the app treat the note as lost.

**The app keeps refused edits from happening (R4-1).** A refusal blocks that note's sync in the app, and a blocked channel stops journaling, so typing after the refused step can be lost when the note closes. That is the fundamentals issue already reported to the owner ("a blocked channel stops journaling"); it is not changed here. Instead the app does not produce an edit the gate refuses:

- `files.capabilities` returns `{ writes }`: true while the gate is on, for any signed-in principal, people and agents alike; false when signed out. It reveals that one switch and nothing else. Agents do not need it: the server refuses what it does not accept, and `attach_file` and the edit tools pass the message on. The app watches it while the live session runs (`file-capability.ts`) and treats files as off until the server says on, and again once the session ends. Convex pushes the change, so turning the gate off reaches open editors at once; the local run below checks this in both directions.
- While off, pasted and dropped content (`safeSlice`, the editor's `transformPasted`, also used for Markdown paste) keeps only file features the note already has, by the same kinds as the server. A file block for another object becomes a paragraph with its name, an image of another object becomes its description (or nothing), and a width the note does not use is dropped. Copying or dragging the note's own attachments within it keeps them. Images copied from the app carry `data-width`, so their width survives HTML copy and paste for any source (R5-3); widths in other web pages' HTML are still dropped.
- While off, a cut whose selection holds a file block, an attachment image or a sized image does nothing and says "Files can't be moved this way yet. Copy, or drag within the note, instead." (R5-2). Pasting it back could not restore them: once cut, the note no longer has them, so the filter and the server would refuse them. This covers every cut event: the keyboard, the context or edit menu, and ProseMirror's own clipboard handling. Copy, dragging within the note (one transaction) and deleting still work.
- While off, undo and redo cannot bring back a file feature the note no longer has (`fileHistoryGate`). That undo does nothing and says "Undo can't bring back removed files or image sizes yet." until files are on again. The note as it is now is the measure, because the removal may reach the server first.
- No toolbar button, slash command or input rule inserts images, file blocks or widths.

Paths that can still reach a refusal through the app, all requiring a note that already has file features:

- an edit made between turning the gate off and the app hearing of it (moments while online; longer offline), including a draft saved on the device while files were on and sent later. This needs files to have been on;
- a collaborator removing an attachment or a width while this device's paste, drag or undo of it is still unsent. This needs only a note with an attachment image, so it can also happen with files never turned on: an image stored before B2 with a well-formed `attachment:<id>` source counts as an attachment image (the read-only scan reports only malformed sources).

Either blocks that note as described above; nothing else is affected.

**Turning files off.** `CONVEX_DEPLOYMENT=dev:decisive-reindeer-520 npx convex env set --prod FILES_WRITES_ENABLED false`. Uploads stop at once, and open apps learn of it through `files.capabilities` within moments while online.

- Keep the readers deployed: Convex, the Worker with its `FILES` binding and the bucket, and an app build that understands file blocks. Notes keep their attachments, and an app from before B2 cannot open a note with a file block. Turning files off stops new file content; it is not a way back to the pre-B2 app.
- While off: no uploads or `attach_file`; no attachment image, width or file block a note does not already have (by kind); a new note with attachments only as a copy naming its source (`sourceNoteIds`, MCP `source_note_ids`). So MCP `create_note` of Markdown with attachments is refused without `source_note_ids`, as is an `edit_note` adding an attachment the note lacks. Text edits, `replace_all` keeping identical attachments, `replace_text`, moving and removing work (the round 4 rollback regression).

Rollout:

1. Create the private R2 bucket `palladian-notes-files`. Deploy the backend and the Worker together, with the gate off: the new app build understands file blocks, and nothing can write them yet. Run the read-only scan (see Deploying) at this point.
2. Wait until every device runs the new build. For this app, the owner confirms each device has loaded it (Settings → About shows the build). The old service worker can only still be serving while one of its windows has stayed open, so every app window on every device must have been closed at least once since the deploy. Collaborators' devices count too: a collaborator still on an old build cannot open a shared note that gains a file block.
3. Turn files on: `CONVEX_DEPLOYMENT=dev:decisive-reindeer-520 npx convex env set --prod FILES_WRITES_ENABLED true`.
4. To turn them off later, see "Turning files off" above.

**Handshake or flag.** An automatic handshake would remove step 2's manual check and cover collaborators' devices: clients report their build, and the server allows file content once every recently active session runs a new one. It needs a build reported per session (A1's device list is the natural place) and a definition of "recently active", which is a policy question. For one owner and a few devices the manual flag is simpler and sufficient. A later step could show, in Settings, which signed-in devices last reported which build, as the checklist for step 2.

### Device concerns left to B3

Clearing the attachment cache at sign-out (D28) and the absence of offline downloads (D84) are client work. The server helps by sending `no-store`, keeping object IDs stable, and providing `noteObjects` for placeholders.

## Differences from plan B1 and B2, deliberately

- **Reads name the note** (`/files/notes/<noteId>/<objectId>`). Convex checks one reference instead of searching every note that might reference the object. A public variant names the link token instead.
- **Two more tables** besides `objects`: `objectRefs` (the per-revision reference record) and `objectDeletions` (the retry-safe byte deletion queue).
- **Editors may read objects from earlier revisions**, so history previews can show them. Readers see only current content, matching the history permission. The plan says nothing on this.
- **A new reference is recorded only if the actor may already use the object.** The plan says "each accepted revision records which objects the current document references"; this adds the authorization check that rule needs.
- **`failed` is for expired or cancelled uploads.** Mismatched bytes leave the ticket usable, so a broken connection can retry.
- **Byte deletion is asynchronous** through the queue and the Worker's existing daily cron. Convex cannot reach R2, and no new secret was added. Bytes are unreachable from the moment of deletion and physically gone within a day; the key is deleted again daily until seven days after any upload lease (tombstones).
- **Never-referenced uploads are removed after 7 days**, even with manual-only retention: they were never in anyone's Trash.
- **At most 200 attachments per note**, so lifecycle work per note stays bounded.
- **Markdown attribute braces** carry `width`, `type` and `size`. The plan names the attributes, not their Markdown form.
- **`attach_file` takes base64 only, up to 2 MB**, not 6 MB as in Deltos, because Palladian's MCP request limit is 4 MiB. No URL source.
- **`attachment:` validation is stricter for new content** (exactly an object ID). Stored documents tolerate the older forms, which grant nothing (review F7); see "Deploying".
- **New optional arguments on protected mutations:** `sourceNoteIds` on `notes.push`, `notes.edit` and `notes.createFromMarkdown`, so a copy can prove access at once; `source_note_ids` on the MCP `create_note` and `edit_note` tools. Apart from the reference rules above, behaviour without them is unchanged.
- **Uploads hold a write lease** (`files.admitUpload` replaced the read-only `uploadTarget`), and deletions are tombstones repeated for seven days after it (review F3, R2-2).
- **The Worker never deletes bytes** (round 3, R3-1). Round 2 had it remove its own late or refused writes; a ticket refused after retries could then delete a ready object's bytes. Only Convex's tombstone sweep deletes now.
- **A files gate** (`FILES_WRITES_ENABLED`, off by default) holds back file features new to a note until every client understands them (R3-3, R4-2). The app asks the server whether files are on and keeps new ones out of paste, drop and undo (R4-1). Pasted web images (`<img width>`) no longer carry a width; images copied from Palladian keep theirs (`data-width`, R5-3), subject to the gate.
- **`history.restore` may reinsert image sources from before attachments.** Only content the server rebuilt from the note's own history is affected; client content stays strict, and such sources still grant nothing (R2-4).

## Found, not changed: history reads of large notes (review R3-4)

This predates this branch and sits in collaborative persistence (`documents.ts`, protected), so it is reported for the owner rather than fixed here.

- **The mechanism.** A checkpoint is written every 100 revisions. Reading a revision (`history.read`, MCP `read_revision`) rebuilds it from the previous checkpoint plus up to 99 steps, and `history.restore` rebuilds both the restored and the current revision. Convex refuses a transaction that reads more than 16 MiB. A read therefore fails once the steps since the last checkpoint add up to about 16 MiB, or about 8 MiB for a restore.
- **Who hits it.** Typing makes steps of a few bytes, so ordinary editing never comes close. Large steps come from replacing much of a note at once:
  - an agent's `replace_all`, or a `replace_text` spanning most of a long note;
  - pasting a large block;
  - a history restore, which is one step the size of the note;
  - a client's saved-version resubmission that falls back to a whole-document step.
- **Sizes.** A note is at most 700 KB, and at most 99 such steps sit between checkpoints. A note under about 160 KB can therefore never reach 16 MiB on a read, and a restore stays safe under about 80 KB. A larger note fails only after dozens of whole-note replacements within one 100-revision interval; the reviewer's case was 35 replacements of about 490 KB.
- **Exposure.** Typical notes are a couple of pages (D31), far below these sizes. The realistic risk is an agent repeatedly rewriting a very long note, which leaves that interval's revisions unreadable and unrestorable until the next checkpoint is passed. The current content is not affected.
- **Proposed fix** (needs its own review): checkpoint by accumulated step bytes as well as by count; restore from the stored current document instead of replaying it; add large-history tests with limits enforced.

## Open questions for the owner

1. **Notes in Trash and Q11.** I kept any object that a note in Trash still contains, beyond the object owner's retention. Should the owner's retention win instead, with that note showing "permanently deleted" when restored?

7. **Deletion timing.** Bytes are physically deleted within a day of permanent deletion (unreachable at once). Is daily enough, or should the sweep run hourly?
